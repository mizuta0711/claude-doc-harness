# 入門ガイド — 最初の1本を書かせるまで

| 項目 | 内容 |
|---|---|
| 対応ハーネス版 | harness-doc 0.11.0 |
| 対象 | 文書ハーネスを**初めて使う人**。このマシンへのプラグインの導入は済んでいる前提（→ [セットアップガイド](セットアップガイド.md)） |
| 前提知識 | Claude Code に日本語で頼めること。コマンドは打たなくてよい |

## この文書でできること

文書ハーネスに何を期待してよいかが分かり、自分のプロジェクトで最初の1本を、決まった手順と点検を通して書かせ、受け取れるようになる。

## 0. このガイドの読み方

| 節 | 内容 |
|---|---|
| 用語 | このガイドに出てくる言葉 |
| 1. 期待値をそろえる | このハーネスが解く問題と、解かない問題 |
| 2. 3つの原則 | 迷ったときの判断の基準 |
| 3. 最初の1本を通す | 導入 → 書かせる → 受け取る、の1周 |
| 4. つまずきポイント | 実際のプロジェクトの文書で試したときに起きたこと |
| 5. 続けるときのコツ | 2本目以降 |

日々の使い分けは [運用ガイド](運用ガイド.md) にある。1本書かせる流れを図で見たいときは [文書作成フロー図](../diagrams/02_文書作成フロー図.md)、ほかの図は [diagrams/](../diagrams/) にある。

## 用語

| 言葉 | 意味 |
|---|---|
| スキル | Claude Code が決まった手順で作業するための手順書。日本語で頼むと、Claude が合うスキルを選んで使う。主なものは下の4行（ほかに、読者や扱う範囲を変える `change-policy` がある） |
| `setup-project` | プロジェクトに文書ハーネスを導入するスキル |
| `plan-doc` | 文書を書く・直す依頼の入口。依頼の大きさ（規模）を判定し、小さな修正はこの中で終える |
| `manual-writer` | 大きな文書を書く・書き直すスキル（`plan-doc` から渡る。直接は頼まない） |
| 改訂設計書 | 大きな文書を書く前に Claude が作る1ページ。受け入れ基準（「読者が文書だけで〇〇できる」）と目次案を書き、承認を受けてから本文に進む |
| `change-tone` | 既存の文書のテイスト（言葉づかいの調子や見た目）だけを変えるスキル（`plan-doc` から渡る。直接は頼まない） |
| 読者役（`doc-reviewer`） | 書き上がった文書を、予備知識のない読者になりきって読み、分かりにくい箇所を指摘する係。文書は書き換えない |
| 致命的・要修正・提案 | 読者役の指摘の重さ。重い順に3段階。**致命的**は読者がゴールに着けない、**要修正**は迷う・誤操作のおそれがある、**提案**はより読みやすくなる。致命的と要修正は直っていなければならない |
| フック（`check-docs`） | 文書を書いた直後に自動で動く検査。曖昧な語・表記の揺れ・リンク切れを見つけると、Claude に直させる |
| `docs-style/` | プロジェクトの文書の決まりを置くフォルダー。用語集・曖昧な語の一覧・文体の決まり（`voice.md`） |
| `CLAUDE.md` | プロジェクトのフォルダーに置く、Claude Code への指示書。Claude は毎回これを読んでから作業する |

## 1. 期待値をそろえる

### 1-1. このハーネスが解く問題

Claude Code にマニュアルを書かせると、分かりにくくなりやすい。原因は3つある。

1. **書き手の順に書く。** 読者がやりたいことの順ではなく、機能の一覧の順に並ぶ
2. **確かめずに書く。** 記憶で書いたコマンドや画面名が、実物と食い違う
3. **曖昧な語で済ませる。** 条件と値を調べる代わりに「`必要に応じて`」と書く

このハーネスは、3つをそれぞれ仕組みで止める。

| 原因 | 止める仕組み |
|---|---|
| 書き手の順 | 書く前に読者とゴールを聞いてくる。受け入れ基準と目次案（改訂設計書）を見せて止まる。書き上がったら読者役が、文書だけで作業できるかを点検する |
| 確かめない | コマンドは実行して出力を写し、確かめられなかったことは完了報告の「問い合わせ」に挙げる（本文では断定しない） |
| 曖昧な語 | 書いた直後にフックが検査し、Claude に直させる |

### 1-2. 期待してよいこと / してはいけないこと

**書かせられる文書:** 利用者が読む文書。マニュアル・手順書・リファレンス・仕様書・README・HTML のサイト。
Markdown と HTML のどちらでも書く（claude-dev-harness を併用しているときの例外は 4-4）。

| 期待してよい | 期待してはいけない |
|---|---|
| 毎回同じ手順で書かれ、読者役の点検とフックの検査を通った文書が出てくる | 一度も読まずにそのまま公開できる文書 |
| プロジェクトの既存の文体・用語・見た目に合わせて書く | Claude が知らない事実（社内の決まり、未実装の予定）を正しく書く |
| 確かめられなかったことが「問い合わせ」として分かる | 実行できない環境（本番サーバー）の手順まで確かめてある |

**AI が書いた文書は下書きである。** 公開するかを決めるのは人で、完了報告の「問い合わせ」の項目は人が確かめる。

### 1-3. 最初に決めておくこと

- **誰が読むか。** 初めて使う人・一般の利用者・開発者・障害時の運用担当、のどれに近いか
- **読み終えたら何ができるべきか。** 「〇〇の設定を終えられる」のように、動詞で言えること

この2つが言えれば、あとは Claude Code が聞いてくる。

## 2. 3つの原則

### 2-1. 書く前に読者を決める

読者が決まっていない文書は、誰にも刺さらない。Claude が読者を聞いてきたら、面倒でも答える。
答えられなければ、Claude は仮定を置いて文書の冒頭に書く。その仮定が合っているかだけは確かめる。

### 2-2. 書いた本人の「分かりやすい」は当てにしない

書いた本人は、書いていないことを頭の中で補って読む。だから本人の点検では分かりにくさを見つけられない。
このハーネスでは、**文書だけを渡された読者役**が点検する。

### 2-3. 決まりは `docs-style/` に残す

その場で「この言葉は使わないで」と頼むだけだと、次の文書では忘れられる。
**決まりにしたいことは、`docs-style/` に書き足すよう頼む。** 例:「〇〇の表記を△△に統一して、用語集に足して」。
書き足した決まりは、フックとスキルが毎回読む。ファイルを自分で開いて編集する必要は無い。

## 3. 最初の1本を通す

全3段階。導入はプロジェクトごとに1回だけで、2本目からは 3-2 から始める。

**途中で許可を求める画面が出たら、許可を選ぶ。** 拒否するとスキルが読めず、何もせずに止まる（→ 4-1）。

1本書かせると、Claude は**3回、返事を待って止まる**（規模と前提の確認、受け入れ基準と目次案、書き上がった後の完了前の確認）。
**読者と扱わないことは、一度決めればブリーフ（文書群ごとの決め事）に残る。** 同じ文書群の2本目からは、読者を聞き直さず、前提を1行で示すだけになる。
所要時間は文書の長さと事実確認の量で変わり、目安はまだ測っていない（未確認）。

### 3-1. プロジェクトに導入する（プロジェクトごとに1回）

セットアップガイドで入れたのは、このマシンの Claude Code 全体へのプラグインである。
ここでは、**文書を書くプロジェクトごとに1回**、そのプロジェクト用の決まりと設定を置く。

**文書を書きたいプロジェクトのフォルダーで Claude Code を開いてから**頼む。別のフォルダーで頼むと、そちらに決まりが置かれる。

```text
このプロジェクトに文書ハーネスを入れて
```

`setup-project` がプロジェクトを調べて、対話で進める。

| プロジェクトの状態 | 聞かれること |
|---|---|
| 既存の文書がある | 検査する文書の場所（複数選択）。読み取った文体を踏襲してよいか。既存の用語表を使うか |
| 文書がまだ無い | 文体（4種類の見本の文から選ぶ）。置き場所と形式（Markdown / HTML）。HTML なら見た目の方向性（シンプル・やさしい大きめ・技術文書の3種類から選ぶ） |

終わると完了報告の表が出る。次の行を見る。

| 見る行 | 確かめること | 合っていないとき |
|---|---|---|
| 導入先 | 自分のプロジェクトのフォルダーの場所か | 正しいフォルダーで Claude Code を開き直し、もう一度頼む |
| 検査対象 | 利用者が読む文書の場所が入っているか | 「`〇〇` も検査対象に入れて」と頼む |
| 文体 | 自分のプロジェクトの文書の調子と合っているか | 「文体を〇〇に変えて」と頼む |
| 試しの検査 | 既存の文書があれば、2本を試しに検査した結果が出る | **数十件出ても導入の失敗ではない**（→ 4-2） |

途中で止まって表が出なかった場合は、同じ文でもう一度頼んでよい。既にあるファイルは上書きされない。

置かれるものは次のとおり。

| 区分 | ファイル |
|---|---|
| 新しく置かれる | `docs-style/` フォルダー（用語集・曖昧な語の一覧・`voice.md`・文書ハーネスの使い方を書いた1ページ・内部の改訂記録）、`.claude/doc-harness.config.json`（検査の設定）、`.claude/rules/doc-brief-*.md`（文書群ごとの読者と扱わないこと） |
| 既存で変わる | `CLAUDE.md` の末尾に節が1つ足されるだけ。既存の文書や CSS は書き換えない |

**増えたファイルは消さない。** 消すとフックが動かなくなる。

### 3-2. 書かせる

```text
ログインの手順書を、初めて使う人向けに書いて。読み終えたら自分でログインできるようにしたい
```

Claude は次の順に進める（入口の `plan-doc` が規模を判定する。新しい手順書は規模 M で、改訂設計書を作ってから `manual-writer` で書く）。

1. 依頼の大きさ（規模）と、読者・ゴールの前提を1〜2行で示して確かめる。**返事を待つ。** 合っていれば「それで進めて」、違えば「読者は〇〇。読み終えたら△△できるようにしたい」と言い直す
2. 改訂設計書を作り、受け入れ基準（「読者が文書だけで〇〇できる」を3〜5個）と目次案を見せる。**返事を待つ。** 良ければ「この設計書で進めて」、違えば「〇〇を先にして」と返す（本文を書いた後で直すより手戻りが小さい）
3. 画面・設定・コマンドを実物で確かめる
4. 本文を書く。書くたびにフックが検査し、指摘があれば Claude が直す。検査の指摘が画面に流れることがあるが、異常ではない。返事は要らない
5. 読者役が受け入れ基準で点検し、Claude が指摘を反映する（2回まで）。返事は要らない
6. 完了前の確認を出す。既存の文書を直したときは、前と後の比べ（本文の字数・見出しの増減・事実の変更の一覧）と、確かめられなかったこと（問い合わせ）が並ぶ。**返事を待つ。** 「このまま採用」「一部を戻す」「やり直す」から選ぶ
7. 改訂の記録（内部の記録と、読者向けの改訂履歴の1行）を残し、完了処理の検査を通す

**小さな修正**（「手順3の数値が違うので直して」）なら、規模 S として、改訂設計書と読者役の点検を省いた短い手順で終わる。返事を待つのは、規模の確認と、事実を変えたときの承認の2回まで。

**コミットは、1つの作業ごとにする。** Claude にコミットを頼むと、改訂の記録が無い文書を含むコミットはフックが止める。前の作業とまとめてコミットすると、どの記録がどの作業のものか見分けられない。

### 3-3. 受け取る

最後に完了報告の表が出る。**「文書」の行に、できたファイルの場所が書いてある。** 次の3つの行を見る。

| 見る行 | 確かめること | 合っていないとき |
|---|---|---|
| 読者とゴール | 頼んだ内容と合っているか | 「読者を〇〇に変えて書き直して」と頼む |
| 読者役レビュー | 致命的・要修正が全件対応済みか。見送った指摘とその理由 | 理由に納得できなければ「見送った△△の指摘を反映して」と頼む |
| 問い合わせ | Claude が確かめられなかった事実（本文には書かず、ここに挙がる） | 自分か、確かめられる人が確かめる。結果を「Q1 を確かめた。結果は□□なので本文を直して」と伝える |

**最後に、できた文書を通して読む。** 「その文書を開いて見せて」と頼めば、Claude が中身を表示する。
読者になったつもりで上から読み、引っかかった箇所を「〇〇の部分が分かりにくい」と伝えれば直す。

## 4. つまずきポイント（実際のプロジェクトの文書で試したときに起きたこと）

### 4-1. スキルを使う許可の確認で止まる

Claude Code の設定によっては、スキルを使うとき・コマンドを実行するときに許可を求める画面が出る。
**許可しないとスキルの中身が読めず、何もせずに止まる。** 許可を選ぶ（画面に出る選択肢の文言は未確認）。
拒否してしまったら、同じ依頼文をもう一度送れば最初からやり直せる。

### 4-2. 既存の文書に、最初から指摘がたくさん出る

導入の最後に、Claude は既存の文書を2本選んで試しに検査し、結果を完了報告に書く（文書は直さない）。
指摘が数十件出ることがある。原因は2つに分かれる。

| 原因 | 見分け方 | 対処 |
|---|---|---|
| 文書の側に本当に曖昧な語がある | 「`なるべく入れてください`」のように、条件が書かれていない | 次にその文書を直すときに直る。まとめて直したければ「この文書の指摘を直して」と頼む |
| ハーネスの決まりがプロジェクトと合っていない | プロジェクトで統一している表記（`サーバ`）が止められている | 文書ではなく決まりを直す。「用語集の〇〇を外して」と頼む |

### 4-3. テイストを変えたら、中身まで変わりそうで不安

テイストの変更は `change-tone` が受け持ち、**事実・手順・画面名・コードは変えない**決まりになっている。
変える前に、`plan-doc` が試作として「今の文」と「変えた後の文」を並べて見せる（HTML なら、試作のページをブラウザーで並べて開ける）。変えたくなければ「やめて」、調整したければ「もう少し〇〇に」と返せば、書き換えは始まらない。
書き換えた後は、差分で中身が変わっていないかを確かめてから、完了前の確認で見せてくる。文体の決まり（`voice.md`）が書き換わるのは、そこで採用したときだけ。

### 4-4. 設計書を頼んだら「対象外」と言われた

**claude-dev-harness（開発用のハーネス）を使っていなければ、この項は読み飛ばしてよい。**

claude-dev-harness を併用しているプロジェクトでは、設計書は claude-dev-harness が扱う。
文書ハーネスが受け持つのは、利用者が読む文書（マニュアル・手順書・サイト・README）である。
設計書を書きたいときは、「harness-core の update-docs で設計書を更新して」のように claude-dev-harness のスキルを名指しして頼む。

## 5. 続けるときのコツ

- **見つけた決まりは `docs-style/` に足すよう頼む。** 「〇〇の表記を△△に統一して、用語集に足して」と頼めば、次の文書からフックが止める
- **文体の見本を育てる。** 「この文はいい」と思う文があれば、「`voice.md` の見本の文に足して」と頼む。設定の表より見本の方がよく効く
- **既存の文書を直すときも `plan-doc` を通す。** 小さな修正なら工程は短く、改訂の記録まで残る。直接書き換えると、改訂の記録が残らない
