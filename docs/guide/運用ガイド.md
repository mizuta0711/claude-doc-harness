## この文書でできること

どの場面でどのスキルを使い、決まり（`docs-style/`）をいつ・どう変えるかを、自分で判断できるようになる。
構造の説明は図に任せ、このガイドは判断だけを扱う。全体は [全体構成図](../diagrams/01_全体構成図.md)、1本書く流れは [文書作成フロー図](../diagrams/02_文書作成フロー図.md)、テイスト変更は [テイスト変更フロー図](../diagrams/05_テイスト変更フロー図.md)、検査は [フック検査の流れ図](../diagrams/04_フック検査の流れ図.md) にある。

## 1. 全体構成（最小限）

ハーネスは**2層**でできている。

| 層 | 置き場所 | 中身 | 誰が直すか |
|---|---|---|---|
| プラグイン | このマシンに1つ（`harness-doc`） | スキル5つ・読者役エージェント・検査フック・見本集・読者プロファイル | ハーネスの開発者。更新はプラグインの更新で全プロジェクトに届く |
| プロジェクト側 | 各プロジェクト | `CLAUDE.md` の節・`docs-style/`（用語集・曖昧語リスト・`voice.md`・使い方）・`.claude/doc-harness.config.json`・ブリーフ（`.claude/rules/doc-brief-*.md`） | **そのプロジェクトの利用者。** 使いながら育てる |

**プロジェクトごとに違うものは、すべてプロジェクト側にある。** プラグインを更新しても、育てた用語集や文体は上書きされない。

## 2. スキルの使い分け

### 2-1. いつ使うか

**文書を書く・直す依頼の入口は `plan-doc` 1つ。** 依頼の性質（新規作成・改訂・誤りの修正・テイスト変更・方針変更）と規模（S/M/L）を判定し、規模に合った工程だけを通す。
規模の判定は Claude が推測し、利用者が最初の問い（規模と前提の確認）で承認する。
利用者が `manual-writer`・`change-tone`・`change-policy` を名指しで頼んでも、`plan-doc` の受付から始まる。

依頼の種類ごとの経路と、利用者が返事をする回数は次のとおり（許可を求める画面は回数に入らない）。
改訂設計書は、受け入れ基準（「読者が文書だけで〇〇できる」）と目次案を書いたファイルで、`docs-style/plans/` に置かれ、中身はチャットにも表示される。

| 依頼 | 規模の目安（どれか1つでも当たれば上の規模） | 経路 | 返事をする回数と、そのとき見せられるもの | 読者役レビュー |
|---|---|---|---|---|
| 小さな修正 | S: 1本・見出しを変えない・直す事実が分かっていて1か所以内 | `plan-doc` の中で終わる | 1〜2回。規模と前提 →（事実を変えた・同じ記述を別の文書でも直した・用語を足したときだけ）完了報告の案で承認 | なし |
| 新しい1本・見出しを変える直し | M: 新規の1本、見出しを増減する、直す事実が2か所以上、図・画面を足す・替える | `plan-doc` → `manual-writer` | 3回。規模と前提 → 改訂設計書 → 完了前の確認（前後確認・問い合わせ） | 書き上げた後 |
| 大きな書き直し | L: 新規の文書群、読者を変える、2本以上にまたがる、「分かりにくいので直して」のように範囲が決まっていない | `plan-doc` → `manual-writer` | 4回。規模と前提 → 目次の段階（ブリーフ・改訂設計書と、読者役が目次案を点検した結果）→ 試作（代表的な節を書いた見本）→ 完了前の確認 | 目次の段階と、書き上げた後 |
| テイスト変更（文体・表記・見た目だけ） | 1本なら M、2本以上か長い1本（要素の種類が多く、代表の1節だけでは調子を決めきれない）なら L | `plan-doc`（試作）→ `change-tone` | 3回（M・L とも）。規模と前提 → 試作（今の文と変えた後の文。改訂設計書の承認も同じ問い）→ 完了前の確認（文体の決まりを書き換えるかも同じ問い）。試作の調整は2回までで、回数に入らない。3回目を頼むと、作り直さずに「今の試作で進める」「やめる」「方針から決め直す（改訂の L にする）」から選ぶよう聞かれる | 書き換えた後（試作の見本と比べる） |
| 方針変更（読者・扱わないこと・事実の承認者・読者向けの改訂履歴の有無） | —（規模の問いは出ない。最初の問いが変える値の案と範囲で、取り違えられたらここで言い直す） | `plan-doc` → `change-policy` | 1〜2回。変える値の案と範囲（依頼文で決まれば省く）→ 影響の一覧を見て「今すぐ直す」か「後で直す」か | なし（直す文書は、上の行の経路で別に通る） |

**方針変更で書き換わるのはブリーフだけである。** 既存の文書は勝手には書き換わらない。`change-policy` が、新しい決め事に合わなくなる文書の一覧と直し方（言い回しだけ／中身から／直さなくてよい）を示す。
「今すぐ直す」を選ぶと、`plan-doc` に渡して直す。言い回しだけで済む文書だけならテイスト変更、中身から直す文書があれば改訂 L にまとめ、1つの改訂設計書で直す。「後で直す」なら、一覧が完了報告に残る。

用語集・曖昧語リスト・config（検査の設定）を変える依頼は、この表に入らない。`plan-doc` を通らず、Claude がその場で直す（[3-2](#3-2-いつ決まりを変えるか)）。

| 場面 | スキル | 頼み方の例 |
|---|---|---|
| プロジェクトで初めて使う | `setup-project` | 「このプロジェクトに文書ハーネスを入れて」 |
| 文書を新しく書く | `plan-doc` → `manual-writer` | 「〇〇の手順書を、△△向けに書いて」 |
| 既存の文書を、伝わるように書き直す | `plan-doc` → `manual-writer` | 「〇〇.md を、初めて使う人が迷わないように書き直して」 |
| 既存の文書の誤りを直す（数値・手順の1か所） | `plan-doc`（S なら中で終わる） | 「手順3の権限の説明が実際と違うので直して」 |
| 既存の文書の調子（文体・表記・見た目）だけを変える | `plan-doc`（試作） → `change-tone` | 「マニュアルをもっとやさしい言葉に変えて」「です・ます調に統一して」 |
| 文書群の読者・扱わないことを変える | `plan-doc` → `change-policy` | 「使い方の対象読者を、手伝う家族に変えたい」「端末の設定も扱うことにしたい」 |
| 読者向けの改訂履歴を付けたい・やめたい、事実の承認者を変えたい | `plan-doc` → `change-policy` | 「使い方の文書にも改訂履歴を付けたい」「事実の確認は〇〇さんに回すことにしたい」 |
| 書いた文書を読者の立場で点検だけしてほしい | `doc-reviewer`（エージェント） | 「この文書を読者目線でレビューして」 |

### 2-2. 迷いやすい組み合わせ

**「書き直す」（`manual-writer`）と「テイストを変える」（`change-tone`）は別物である。**

| | `manual-writer` | `change-tone` |
|---|---|---|
| 変えるもの | 構成・中身・言い回しのすべて | 言い回し・文末・表記・見た目だけ |
| 変えないもの | 事実（確かめ直す） | 事実・手順の順番と数・画面名・コード・見出しの構成 |
| 向いている場面 | 読者が迷う、手順が飛んでいる、情報が古い | 中身は正しいが、調子が読者に合っていない |

**どちらにするかは `plan-doc` が判定する**（利用者が選ばなくてよい）。「分かりにくい」の原因が中身にあるなら `manual-writer`、調子にあるなら `change-tone` に渡す。
テイストを変えるつもりでも、前提や用語の説明を足さないと読者に届かないなら、中身を直す（改訂）として扱う。
両方が要るなら、中身を直す改訂として頼む。規模 L なら試作で調子も合わせるので、テイスト変更を別に頼まなくてよい。規模 M では試作が無いので、調子が合わなければ、直した後でテイスト変更を頼む（逆の順だと、中身の書き直しで調子が崩れる）。
判定に納得できなければ、最初の問い（規模と前提の確認）で言い直す。この問いは選択肢の画面で出るので、選択肢に無い答えは自由入力の欄に「テイスト変更として扱って」「規模 M として進めて」のように書く。

## 3. 決まり（`docs-style/`）の育て方

### 3-1. どのファイルが何を決めるか

| ファイル | 決めること | 書いたときに機械で検査されるか |
|---|---|---|
| `glossary.md` | 用語と表記（推奨 / 禁止） | される（禁止表記） |
| `banned-words.txt` | 使わない曖昧な語 | される |
| `voice.md` | 文体（文末・温度・専門用語・一文の長さ）と見た目（従う CSS・図の描き方） | 文末だけされる（config の `voice.endings` を設定したとき。値は導入時に決まり、テイスト変更で文末を変えたときに書き換わる）。ほかは読者役が点検する |
| `.claude/doc-harness.config.json` | 検査する文書の場所、既存の用語表、文末の検査 | — |

| ブリーフ（`.claude/rules/doc-brief-<名前>.md`） | 文書群ごとの読者・扱わないこと・事実の承認者・読者向けの改訂履歴の有無・文体の差分。文書ごとのゴール・種類・受け入れ基準 | されない。書く人が `manual-writer` で引き、読者役にも届く（Claude Code が、対象の文書を読んだときに自動で読み込む） |

「検査される」は、文書を書いた直後に指摘が Claude に返り、Claude がその場で直すという意味である（[5](#5-書くたびの検査check-docs-フック)）。利用者の操作を待って止まるのでも、コミットを止めるのでもない。

### 3-2. いつ決まりを変えるか

**同じ指摘を2回見たら、決まりを疑う。**

| 状況 | 変えるもの |
|---|---|
| プロジェクトで統一している表記が止められる | `glossary.md` から外す、または推奨と禁止を入れ替える |
| 正しい使い方の語まで止められる | `banned-words.txt` から外す。1か所だけなら行末に `<!-- check-docs: ignore 理由 -->` |
| 同じ語の表記が文書ごとに揺れている | `glossary.md` に足す |
| 読者役が毎回「硬い」「くだけすぎ」と指摘する | `voice.md` の見本の文を差し替える（「文書をもっとやさしい言葉にして」と頼めば、テイスト変更として試作から直し、採用したときに `voice.md` も書き換わる） |
| 検査してほしくない文書で止まる | config の `exclude` に足す |
| 読者役が毎回、文書の範囲の外のこと（端末の設定）を書けと指摘する | ブリーフの「扱わないこと」に足す（方針変更として頼む。「〇〇は扱わないことにしたい」）。読者役は「扱わないこと」に当たる指摘を致命的にしなくなる |
| 文書を書くたびに読者を聞かれる | ブリーフが無いか、項目が欠けている。`.claude/rules/` に `doc-brief-` で始まるファイルが無ければ「このプロジェクトに文書ハーネスを入れて」と頼む（足りないものだけが足される） |

変えるときは Claude Code に頼めばよい（「用語集の〇〇を外して」）。

- **経路:** 用語集・曖昧語リスト・config の変更は `plan-doc` を通らず、Claude がその場で直す。用語集に語を足すときは、足す語（推奨と禁止の表記）を示して、足してよいかを利用者に確かめてくる。`voice.md` の文体を変えるならテイスト変更、ブリーフを変えるなら方針変更として `plan-doc` を通る（2-1 の表）
- **既存の文書への影響:** 決まりを変えても、既存の文書は書き換わらない。次にその文書を書いたときに、新しい決まりで検査される。そのとき Claude が古い違反もその場で直す。ただし完了処理の検査が止めるのは、作業前より指摘が増えたときだけで、前からあった違反では止めない
- **既存の文書をまとめて合わせたいとき:** 「用語集の変更に合わせて、〇〇の文書群の表記を直して」と頼む。表記の統一はテイスト変更として扱われる（2本以上なら規模 L）
- **記録:** 決まりのファイルは検査する文書ではないので、改訂の記録は要らず、コミット時の検査にも止められない
- `glossary.md` と `banned-words.txt` は自分で開いて直してもよい。`voice.md` は手で直さず Claude に頼む（文末を変えると config の `voice.endings` も変える必要があり、手で直すと検査が古い文末のまま指摘し続ける）。`.claude/` 配下の設定とブリーフは、スキルがスクリプトで書き込む（手で直すと書式が崩れる）

### 3-3. 曖昧語の扱い

初期値の曖昧語リストは「条件と値を書けば言い換えられる語」に絞ってある。
`など` は例を挙げる正しい使い方が多いため、初期値では止めない。手順書だけのプロジェクトで止めたい場合は、`banned-words.txt` の `# など` の `#` を外す。

## 4. 読者役レビューと改訂履歴

### 4-1. 読者役レビューの扱い

読者役レビューは規模 M・L（[2-1](#2-1-いつ使うか) の表）の文書で行う（S の小さな修正では省く）。

- **受け入れ基準で判定する。** 改訂設計書で目次案と一緒に決めた「読者が文書だけで〇〇できる」を基準ごとに判定し、基準を満たせない原因になる指摘を致命的にする。ブリーフの「扱わないこと」に当たる指摘は致命的にしない
- **2回で終える。**（書き上げた後の点検の上限。L の目次の段階の点検は、それとは別に1回）1回目で致命的・要修正が0なら終わり。直したら新しい読者役でもう1回。**2回まわしても基準を満たさなければ、3回目をまわさず、利用者に判断を渡す**（基準を直す・範囲外とする・もう1回まわす）
- **指摘は全件に「対応済み」か「見送り（理由）」が付く。** 一覧は完了報告の「読者役レビュー」の行に出る。 見送りの理由は「書き手の都合」になっていないかを見る
- **読者役は書き手の意図を知らずに読み、Claude が意図と照らして反映を決める。** 改訂意図を理由に見送ったときは、どの意図によるかが書いてある。同じ箇所への指摘が2回見送られたら、意図を保つか変えるかを聞かれる
- **読者役も間違える。** 指摘が事実と違うときは、実物で確かめてから見送ってよい。完了報告の「誤っていた指摘」に残る

### 4-2. 改訂履歴

**改訂の記録は必ず残る。** 2つの層がある。記録はスキルが作業の終わりに書くので、利用者が書く必要は無い。

| 層 | いつ残るか | 中身 | 置き場所 |
|---|---|---|---|
| 内部の改訂記録 | すべての文書・すべての変更（小さな修正も） | 改訂箇所・改訂内容・**改訂意図**・根拠・見送ったこと | `docs-style/history/<文書群>.md`。読者には見せない |
| 読者向けの改訂履歴 | ブリーフで「あり」の文書だけ | いつ・どこを・どう変えたか（1行） | 文書の末尾の「改訂履歴」の節 |

内部の改訂記録は、**次に直すときに読まれる**（これまでの改訂意図と見送ったことを踏まえて直すため）。読者役のレビューには渡されない。

記録が残ったかは、2つの検査が確かめる。

| 検査 | いつ走るか | 見るもの | 見つかったとき |
|---|---|---|---|
| 完了処理の検査（`complete-doc.mjs`） | スキルが作業を終える直前（完了報告の前） | 直した文書ごとに内部の改訂記録があるか。読者向けの改訂履歴が「あり」なら、文書に1行足されたか。M・L では、改訂設計書の受け入れ基準とタスクにチェックが付いたか、前後確認（作業の前と後の比べ）が書かれたか。`check-docs` の指摘が作業前より増えていないか。改行コードが変わっていないか。試作のファイル（試作のために元の文書の隣に作る `<名前>.proto-1.<拡張子>`）が残っていないか | Claude が直してから完了報告を出す。結果は完了報告の「完了処理の検査」の行に載る |
| コミット時の検査（`commit-check` フック） | Claude Code の中で Claude が `git commit` するとき（自分でターミナルからコミットしたときは走らない。検査を通したいなら Claude にコミットを頼む） | コミットに入る文書ごとに、改訂の記録が同じコミットに入っているか。読者向けの改訂履歴が「あり」なら、文書に1行足されているか。M・L なら改訂設計書も入っていて、チェックと前後確認がそろっているか。試作のファイルが入っていないか | コミットを止める（下の表）。本文に問い合わせの印（`<!-- 問い合わせ: Q1 -->`。確かめられなかった事実の箇所に置かれ、回答を待つあいだは残っていてよい）が残っているだけなら、警告を出してコミットは通す |

**比べる相手が違う。** 完了処理の検査は、作業の始めにスキルが取った文書の控え（基準点。`.git/harness-doc/` に置かれ、コミットされない）と比べる。控えがあるので、作業のたびにコミットしなくても、前の作業の記録を今の作業の記録と取り違えない。
コミット時の検査は、直前のコミットと比べる（`--amend` なら1つ前）。文書ごとに記録が1つでも足されていれば通すので、2つの作業をまとめてコミットすると、片方の作業の記録が抜けていても気づけない。**だから1つの作業ごとにコミットする。**
スキルを通さずに文書を直したときは、控えが無く、完了処理の検査も走らない。そのまま Claude にコミットを頼むと、コミット時の検査が直前のコミットと比べて、記録が無ければ止める（下の表の1行目）。「記録を足してからコミットして」と頼めばよい。
完了処理の検査が「判定できない」と報告するのは、控えを取らずに記録を足した後で検査を走らせたとき（前の作業の記録と区別できない）。そのときは完了報告に今回足した記録が示されるので、それが今回の作業のものかを確かめる。

#### コミットが止まったとき

止まると `[harness-doc commit-check] ❌ 改訂の記録が無い文書を含むコミット` で始まる表示が出る（理由が改訂の記録でなくても1行目は同じ。理由は2行目から後）。

| 2行目から後に書いてあること | 原因 | 対処 |
|---|---|---|
| 内部の改訂記録に、この文書の節が足されていない | スキルを通さずに直した | 「記録を足してからコミットして」と頼む。記録が要らない正当な変更（ほかのハーネスや整形ツールが直した）なら、そう伝える（下の承認になる） |
| 改訂設計書（…）がこのコミットに入っていない | M・L の改訂設計書（`docs-style/plans/completed/`）をコミットに入れていない | 「改訂設計書も一緒にコミットして」 |
| 試作のファイルがコミットに入っている | 試作（`<名前>.proto-1.<拡張子>`）を消し忘れた | 「試作のファイルを消して、コミットからも外して」 |
| 別の呼び出しに分ける | ファイルを変えるコマンドとコミットを1つにつないだ | 頼まなくてよい。Claude が分けてやり直す |
| 検査が時間内に終わらなかった | 1回のコミットに文書が多すぎる | 「文書を分けてコミットして」 |

表に無い理由（改訂意図が空・改訂設計書のパスが記録に無い・文書に改訂履歴の節が無い・ブリーフが当たらない）のときは、2行目から後をそのまま Claude に示し、「この理由を直してからコミットして」と頼む。

**記録を残さずにコミットするときは、許可の画面で承認を求められる。** Claude がコミットの文言に `doc-record: skip（改訂の記録なしでコミットする: <理由>）` を書くと、検査は止めずに、ふつうのコマンドの実行確認と同じ画面を出す（許可を省く設定でも出る）。
画面のコマンドの中のこの文言と理由を読み、記録が要らないと分かっているときだけ許可する。許可すればそのままコミットされ、記録は残らない。拒否すればコミットされないので、「記録を足して」と頼む。
理由の形が違う `doc-record: skip` は、承認を求めずに止める。

## 5. 書くたびの検査（`check-docs` フック）

コミットのときに走る検査は 4-2 にある。この節は、文書を書くたびに走る検査だけを扱う。

| 項目 | 挙動 |
|---|---|
| いつ走るか | Claude が Write / Edit で、config で検査対象にした場所の `.md`・`.html` を書いた直後 |
| 何を見るか | 曖昧語・用語集・リンク切れ・アンカー切れ（`#` 以降の見出しが行き先にあるか）・必須見出し（文書の種類ごとに要る見出し。[check-docs 仕様](../reference/check-docs仕様.md)）・文末の混在。Markdown はコードブロックの言語指定も |
| アンカー切れ | 書いた文書から出ていくリンクだけを見る。**見出しの文言を変えると、ほかの文書からそこへのリンクが切れても気づけない**ので、見出しを変えたら `#見出し` で検索して直す。見出しからアンカーを作る規則が GitHub と違う描画（静的サイト生成）では「アンカー切れの検査を止めて」と頼む |
| 違反があったら | 指摘が Claude に返り、Claude がその場で直す。利用者の操作は要らない。指摘は Claude Code の画面にも流れる |
| 誤検知・直したくない指摘 | 正しい語が止められた、直した結果が意図と違う言い換えになった、同じ指摘が繰り返されるときは、Claude に止めるよう伝え、決まりのほうを直す（[3-2](#3-2-いつ決まりを変えるか) の表）。1か所だけなら行末に `<!-- check-docs: ignore 理由 -->` を書くよう頼む |
| 設定が無いプロジェクト | 何もしない。プラグインを全プロジェクトに入れても邪魔にならない |
| HTML の何を読むか | 本文の文字だけ。`script`・`style`・`pre`・`code` とタグの属性は読まない |
| 構造とアクセシビリティ | 画像の代替テキスト・見出しレベルの飛び・「こちら」だけのリンク・HTML の `lang` も見る。見出しの飛びも、ほかと同じく止まる（WCAG では不適合ではなく推奨だが、初期値で検査する）。意図して使っているなら「見出しの飛びの検査を止めて」と頼む |

検査項目の詳細は [check-docs 仕様](../reference/check-docs仕様.md) にある。

## 6. 書く前に読む知見のまとめ

`manual-writer` は、構成（Diátaxis）・文章（Google / Microsoft）・日本語の表記（JTF・公用文作成の考え方）・Web での読まれ方（NN/g・GOV.UK）・アクセシビリティ（WCAG 2.2・デジタル庁）の要点を、出典つきのまとめとして読んでから書く。
**資料どうしで扱いが違う項目（長音・数字の全角半角・括弧内の句点）は、まとめではなく `voice.md` と用語集が決める。**
まとめの中身は Claude Code に「文書ハーネスの知見のまとめの、アクセシビリティの部分を見せて」のように、上の分野の名前で頼めば表示される。

## 7. claude-dev-harness と併用するとき

claude-dev-harness は開発用のハーネスで、harness-core はその中心のプラグインの名前である。

| 文書 | 受け持つ側 |
|---|---|
| 利用者が読む文書（マニュアル・手順書・サイト・README） | 文書ハーネス（入口は `plan-doc`） |
| 設計書・機能設計書・レビュー記録・引き継ぎ（`docs/設計書/`・`docs/features/`・`docs/reviews/`・`docs/handoff/`） | harness-core（`update-docs` ほか） |

- 導入時に、harness-core が管理するフォルダは自動で検査対象から外れる
- harness-core の用語表（`.claude/rules/` の用語集）があれば、導入時に検査にも使うかを聞かれる。使うと用語表が1つにまとまる
- 実装を変えたら設計書は harness-core が更新する。**利用者向けの文書も変わる場合は、別に `plan-doc` に頼んで直す**（改訂の記録も残る）
