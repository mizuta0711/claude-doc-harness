# 運用ガイド — 使い分けと判断の基準

| 項目 | 内容 |
|---|---|
| 対応ハーネス版 | harness-doc 0.6.0 |
| 対象 | 一度、文書を1本通した人。**日々の判断の基準**を置く |
| 前に読む | [入門ガイド](入門ガイド.md) |

## この文書でできること

どの場面でどのスキルを使い、決まり（`docs-style/`）をいつ・どう変えるかを、自分で判断できるようになる。
構造の説明は [図](../diagrams/) に任せ、このガイドは判断だけを扱う。

## 1. 全体構成（最小限）

ハーネスは**2層**でできている。

| 層 | 置き場所 | 中身 | 誰が直すか |
|---|---|---|---|
| プラグイン | このマシンに1つ（`harness-doc`） | スキル3つ・読者役エージェント・検査フック・見本集・読者プロファイル | ハーネスの開発者。更新はプラグインの更新で全プロジェクトに届く |
| プロジェクト側 | 各プロジェクト | `CLAUDE.md` の節・`docs-style/`（用語集・曖昧語リスト・`voice.md`・使い方）・`.claude/doc-harness.config.json` | **そのプロジェクトの利用者。** 使いながら育てる |

**プロジェクトごとに違うものは、すべてプロジェクト側にある。** プラグインを更新しても、育てた用語集や文体は上書きされない。

## 2. スキルの使い分け

### 2-1. いつ使うか

| 場面 | スキル | 頼み方の例 |
|---|---|---|
| プロジェクトで初めて使う | `setup-project` | 「このプロジェクトに文書ハーネスを入れて」 |
| 文書を新しく書く | `manual-writer` | 「〇〇の手順書を、△△向けに書いて」 |
| 既存の文書を、伝わるように書き直す | `manual-writer` | 「〇〇.md を、初めて使う人が迷わないように書き直して」 |
| 既存の文書の調子（文体・表記・見た目）だけを変える | `change-tone` | 「マニュアルをもっとやさしい言葉に変えて」「です・ます調に統一して」 |
| 書いた文書を読者の立場で点検だけしてほしい | `doc-reviewer`（エージェント） | 「この文書を読者目線でレビューして」 |

### 2-2. 迷いやすい組み合わせ

**「書き直す」（`manual-writer`）と「テイストを変える」（`change-tone`）は別物である。**

| | `manual-writer` | `change-tone` |
|---|---|---|
| 変えるもの | 構成・中身・言い回しのすべて | 言い回し・文末・表記・見た目だけ |
| 変えないもの | 事実（確かめ直す） | 事実・手順の順番と数・画面名・コード・見出しの構成 |
| 向いている場面 | 読者が迷う、手順が飛んでいる、情報が古い | 中身は正しいが、調子が読者に合っていない |

「分かりにくい」の原因が中身にあるなら `manual-writer`、調子にあるなら `change-tone`。
両方なら、**先に `manual-writer` で中身を直し、次に `change-tone`** の順にする（逆だと書き直しで調子が崩れる）。

## 3. 決まり（`docs-style/`）の育て方

### 3-1. どのファイルが何を決めるか

| ファイル | 決めること | 機械で止まるか |
|---|---|---|
| `glossary.md` | 用語と表記（推奨 / 禁止） | 止まる（禁止表記） |
| `banned-words.txt` | 使わない曖昧な語 | 止まる |
| `voice.md` | 文体（文末・温度・専門用語・一文の長さ）と見た目（従う CSS・図の描き方） | 文末だけ止まる（`voice.endings` を設定したとき）。ほかは読者役が点検する |
| `.claude/doc-harness.config.json` | 検査する文書の場所、既存の用語表、文末の検査 | — |

### 3-2. いつ決まりを変えるか

**同じ指摘を2回見たら、決まりを疑う。**

| 状況 | 変えるもの |
|---|---|
| プロジェクトで統一している表記が止められる | `glossary.md` から外す、または推奨と禁止を入れ替える |
| 正しい使い方の語まで止められる | `banned-words.txt` から外す。1か所だけなら行末に `<!-- check-docs: ignore 理由 -->` |
| 同じ語の表記が文書ごとに揺れている | `glossary.md` に足す |
| 読者役が毎回「硬い」「くだけすぎ」と指摘する | `voice.md` の見本の文を差し替える（`change-tone` に頼めば一緒に直す） |
| 検査してほしくない文書で止まる | config の `exclude` に足す |

変えるときは Claude Code に頼めばよい（「用語集の〇〇を外して」）。`.claude/` 配下の設定は、スキルがスクリプトで書き込む。

### 3-3. 曖昧語の扱い

初期値の曖昧語リストは「条件と値を書けば言い換えられる語」に絞ってある。
`など` は例を挙げる正しい使い方が多いため、初期値では止めない。手順書だけのプロジェクトで止めたい場合は、`banned-words.txt` の `# など` の `#` を外す。

## 4. 読者役レビューの扱い

- **指摘は全件に「対応済み」か「見送り（理由）」が付く。** 見送りの理由は「書き手の都合」になっていないかを見る
- **致命的が残っているうちは完成にしない。** 致命的は「読者がゴールに到達できない」指摘である
- **読者役も間違える。** 指摘が事実と違うときは、実物で確かめてから見送ってよい
- 2回目のレビューで致命的が0になれば、3回目は要らない

## 5. フックの挙動

| 項目 | 挙動 |
|---|---|
| いつ走るか | Claude が Write / Edit で `.md`・`.html` を書いた直後 |
| 何を見るか | 曖昧語・用語集・リンク切れ・アンカー切れ（`#` 以降の見出しが行き先にあるか）・必須見出し・文末の混在。Markdown はコードブロックの言語指定も |
| アンカー切れ | 書いた文書から出ていくリンクだけを見る。**見出しの文言を変えると、ほかの文書からそこへのリンクが切れても気づけない**ので、見出しを変えたら `#見出し` で検索して直す。見出しからアンカーを作る規則が GitHub と違う描画（静的サイト生成）では「アンカー切れの検査を止めて」と頼む |
| 違反があったら | 指摘が Claude に返り、Claude がその場で直す。利用者の操作は要らない |
| 設定が無いプロジェクト | 何もしない。プラグインを全プロジェクトに入れても邪魔にならない |
| HTML の何を読むか | 本文の文字だけ。`script`・`style`・`pre`・`code` とタグの属性は読まない |
| 構造とアクセシビリティ | 画像の代替テキスト・見出しレベルの飛び・「こちら」だけのリンク・HTML の `lang` も見る。見出しの飛びは推奨の扱いで、意図して使っているなら「見出しの飛びの検査を止めて」と頼む |

### 5-1. 知見のまとめ

`manual-writer` は、構成（Diátaxis）・文章（Google / Microsoft）・日本語の表記（JTF・公用文作成の考え方）・Web での読まれ方（NN/g・GOV.UK）・アクセシビリティ（WCAG 2.2・デジタル庁）の要点を、出典つきのまとめとして読んでから書く。
**資料どうしで扱いが違う項目（長音・数字の全角半角・括弧内の句点）は、まとめではなく `voice.md` と用語集が決める。**
まとめの中身は Claude Code に「文書ハーネスの〇〇のまとめを見せて」と頼めば表示される。

検査項目の詳細は [check-docs 仕様](../reference/check-docs仕様.md) にある。

## 6. claude-dev-harness と併用するとき

| 文書 | 受け持つ側 |
|---|---|
| 利用者が読む文書（マニュアル・手順書・サイト・README） | 文書ハーネス（`manual-writer`・`change-tone`） |
| 設計書・機能設計書・レビュー記録・引き継ぎ（`docs/設計書/`・`docs/features/`・`docs/reviews/`・`docs/handoff/`） | harness-core（`update-docs` ほか） |

- 導入時に、harness-core が管理するフォルダは自動で検査対象から外れる
- harness-core の用語表（`.claude/rules/` の用語集）があれば、導入時に検査にも使うかを聞かれる。使うと用語表が1つにまとまる
- 実装を変えたら設計書は harness-core が更新する。**利用者向けの文書も変わる場合は、別に `manual-writer` で直す**
