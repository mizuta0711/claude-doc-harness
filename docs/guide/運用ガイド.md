# 運用ガイド — 使い分けと判断の基準

| 項目 | 内容 |
|---|---|
| 対応ハーネス版 | harness-doc 0.10.0 |
| 対象 | 一度、文書を1本通した人。**日々の判断の基準**を置く |
| 前に読む | [入門ガイド](入門ガイド.md) |

## この文書でできること

どの場面でどのスキルを使い、決まり（`docs-style/`）をいつ・どう変えるかを、自分で判断できるようになる。
構造の説明は [図](../diagrams/) に任せ、このガイドは判断だけを扱う。

## 1. 全体構成（最小限）

ハーネスは**2層**でできている。

| 層 | 置き場所 | 中身 | 誰が直すか |
|---|---|---|---|
| プラグイン | このマシンに1つ（`harness-doc`） | スキル5つ・読者役エージェント・検査フック・見本集・読者プロファイル | ハーネスの開発者。更新はプラグインの更新で全プロジェクトに届く |
| プロジェクト側 | 各プロジェクト | `CLAUDE.md` の節・`docs-style/`（用語集・曖昧語リスト・`voice.md`・使い方）・`.claude/doc-harness.config.json`・ブリーフ（`.claude/rules/doc-brief-*.md`） | **そのプロジェクトの利用者。** 使いながら育てる |

**プロジェクトごとに違うものは、すべてプロジェクト側にある。** プラグインを更新しても、育てた用語集や文体は上書きされない。

## 2. スキルの使い分け

### 2-1. いつ使うか

**文書を書く・直す依頼の入口は `plan-doc` 1つ。** 依頼の性質と規模（S/M/L）を判定し、規模に合った工程だけを通す。
小さな修正（S: 1本・見出しを変えない・直す事実が1か所）は `plan-doc` の中で終わり、改訂設計書と読者役レビューを省く。
大きな作業（M・L）は、`plan-doc` が改訂設計書（受け入れ基準と目次案）を作って承認を取り、`manual-writer` で書く。テイスト変更は `change-tone` に渡る。規模の判定は Claude が推測し、利用者が承認する。
利用者が `manual-writer`・`change-policy` を名指しで頼んでも、`plan-doc` の受付から始まる。

| 場面 | スキル | 頼み方の例 |
|---|---|---|
| プロジェクトで初めて使う | `setup-project` | 「このプロジェクトに文書ハーネスを入れて」 |
| 文書を新しく書く | `plan-doc` → `manual-writer` | 「〇〇の手順書を、△△向けに書いて」 |
| 既存の文書を、伝わるように書き直す | `plan-doc` → `manual-writer` | 「〇〇.md を、初めて使う人が迷わないように書き直して」 |
| 既存の文書の誤りを直す（数値・手順の1か所） | `plan-doc`（S なら中で終わる） | 「手順3の権限の説明が実際と違うので直して」 |
| 既存の文書の調子（文体・表記・見た目）だけを変える | `plan-doc` → `change-tone` | 「マニュアルをもっとやさしい言葉に変えて」「です・ます調に統一して」 |
| 文書群の読者・扱わないことを変える | `plan-doc` → `change-policy` | 「使い方の対象読者を、手伝う家族に変えたい」「端末の設定も扱うことにしたい」 |
| 書いた文書を読者の立場で点検だけしてほしい | `doc-reviewer`（エージェント） | 「この文書を読者目線でレビューして」 |

### 2-2. 迷いやすい組み合わせ

**「書き直す」（`manual-writer`）と「テイストを変える」（`change-tone`）は別物である。**

| | `manual-writer` | `change-tone` |
|---|---|---|
| 変えるもの | 構成・中身・言い回しのすべて | 言い回し・文末・表記・見た目だけ |
| 変えないもの | 事実（確かめ直す） | 事実・手順の順番と数・画面名・コード・見出しの構成 |
| 向いている場面 | 読者が迷う、手順が飛んでいる、情報が古い | 中身は正しいが、調子が読者に合っていない |

**どちらにするかは `plan-doc` が判定する**（利用者が選ばなくてよい）。「分かりにくい」の原因が中身にあるなら `manual-writer`、調子にあるなら `change-tone` に渡す。
テイストを変えるつもりでも、前提や用語の説明を足さないと読者に届かないなら、中身を直す（改訂）として扱う。
両方が要るなら、**先に `manual-writer` で中身を直し、次に `change-tone`** の順にする（逆だと書き直しで調子が崩れる）。判定に納得できなければ、規模の確認の問いで言い直す。

## 3. 決まり（`docs-style/`）の育て方

### 3-1. どのファイルが何を決めるか

| ファイル | 決めること | 機械で止まるか |
|---|---|---|
| `glossary.md` | 用語と表記（推奨 / 禁止） | 止まる（禁止表記） |
| `banned-words.txt` | 使わない曖昧な語 | 止まる |
| `voice.md` | 文体（文末・温度・専門用語・一文の長さ）と見た目（従う CSS・図の描き方） | 文末だけ止まる（`voice.endings` を設定したとき）。ほかは読者役が点検する |
| `.claude/doc-harness.config.json` | 検査する文書の場所、既存の用語表、文末の検査 | — |
| ブリーフ（`.claude/rules/doc-brief-<名前>.md`） | 文書群ごとの読者・扱わないこと・事実の承認者・読者向けの改訂履歴の有無・文体の差分。文書ごとのゴール・種類・受け入れ基準 | 止まらない。書く人が `manual-writer` で引き、読者役にも届く（Claude Code が、対象の文書を読んだときに自動で読み込む） |

### 3-2. いつ決まりを変えるか

**同じ指摘を2回見たら、決まりを疑う。**

| 状況 | 変えるもの |
|---|---|
| プロジェクトで統一している表記が止められる | `glossary.md` から外す、または推奨と禁止を入れ替える |
| 正しい使い方の語まで止められる | `banned-words.txt` から外す。1か所だけなら行末に `<!-- check-docs: ignore 理由 -->` |
| 同じ語の表記が文書ごとに揺れている | `glossary.md` に足す |
| 読者役が毎回「硬い」「くだけすぎ」と指摘する | `voice.md` の見本の文を差し替える（`change-tone` に頼めば一緒に直す） |
| 検査してほしくない文書で止まる | config の `exclude` に足す |
| 読者役が毎回、文書の範囲の外のこと（端末の設定）を書けと指摘する | ブリーフの「扱わないこと」に足す（`change-policy` に頼む）。読者役は「扱わないこと」に当たる指摘を致命的にしなくなる |
| 文書を書くたびに読者を聞かれる | ブリーフが無いか、項目が欠けている。0.6.0 以前に導入したプロジェクトなら「文書ハーネスにブリーフを足して」と頼む |

変えるときは Claude Code に頼めばよい（「用語集の〇〇を外して」）。`.claude/` 配下の設定は、スキルがスクリプトで書き込む。

### 3-3. 曖昧語の扱い

初期値の曖昧語リストは「条件と値を書けば言い換えられる語」に絞ってある。
`など` は例を挙げる正しい使い方が多いため、初期値では止めない。手順書だけのプロジェクトで止めたい場合は、`banned-words.txt` の `# など` の `#` を外す。

## 4. 読者役レビューと改訂履歴

### 4-1. 読者役レビューの扱い

読者役レビューは規模 M・L の文書で行う（S の小さな修正では省く）。

- **受け入れ基準で判定する。** 改訂設計書で目次案と一緒に決めた「読者が文書だけで〇〇できる」を基準ごとに判定し、基準を満たせない原因になる指摘を致命的にする。ブリーフの「扱わないこと」に当たる指摘は致命的にしない
- **2回で終える。** 1回目で致命的・要修正が0なら終わり。直したら新しい読者役でもう1回。**2回まわしても基準を満たさなければ、3回目をまわさず、利用者に判断を渡す**（基準を直す・範囲外とする・もう1回まわす）
- **指摘は全件に「対応済み」か「見送り（理由）」が付く。** 見送りの理由は「書き手の都合」になっていないかを見る
- **読者役は書き手の意図を知らずに読み、Claude が意図と照らして反映を決める。** 改訂意図を理由に見送ったときは、どの意図によるかが書いてある。同じ箇所への指摘が2回見送られたら、意図を保つか変えるかを聞かれる
- **読者役も間違える。** 指摘が事実と違うときは、実物で確かめてから見送ってよい。完了報告の「誤っていた指摘」に残る

### 4-2. 改訂履歴

**改訂の記録は必ず残る。** 2つの層がある。

| 層 | いつ残るか | 中身 | 置き場所 |
|---|---|---|---|
| 内部の改訂記録 | すべての文書・すべての変更（小さな修正も） | 改訂箇所・改訂内容・**改訂意図**・根拠・見送ったこと | `docs-style/history/<文書群>.md`。読者には見せない |
| 読者向けの改訂履歴 | ブリーフで「あり」の文書だけ | いつ・どこを・どう変えたか（1行） | 文書の末尾の「改訂履歴」の節 |

内部の改訂記録は、**次に直すときに読まれる**（これまでの改訂意図と見送ったことを踏まえて直すため）。読者役のレビューには渡されない。
完了報告の前に、完了処理の検査（`complete-doc.mjs`）が記録の有無を確かめ、結果を報告に載せる。M・L では、改訂設計書の受け入れ基準とタスクのチェック、前後確認が書かれているかも見る。
Claude がコミットするときは、フック（`commit-check`）がコミットの中身を確かめ、記録の無い文書があれば止める。harness-doc の工程を通さない正当な変更（ほかのハーネスが直した README のような変更）は、コミットの文言に `doc-record: skip（理由）` を書くと、利用者に承認を求める問いが出る。
検査は、スキルが作業の始めに記録した基準点と比べる（基準点は `.git/` の中に置かれ、コミットされない）。基準点があれば、作業のたびにコミットしなくても、前の作業の記録で通ってしまうことはない。
基準点が無いまま記録を足すと、「判定できない」と報告される（前の作業の記録と区別できないため。スキルを通さずに直したときに起きる）。
同じ検査で、書き換えた文書の `check-docs` の指摘が作業前より増えていないか、改行コードが変わっていないかも見る（スキルが検査を走らせたときだけ。フックと違い、書くたびには走らない）。

## 5. フックの挙動

| 項目 | 挙動 |
|---|---|
| いつ走るか | Claude が Write / Edit で `.md`・`.html` を書いた直後 |
| 何を見るか | 曖昧語・用語集・リンク切れ・アンカー切れ（`#` 以降の見出しが行き先にあるか）・必須見出し・文末の混在。Markdown はコードブロックの言語指定も |
| アンカー切れ | 書いた文書から出ていくリンクだけを見る。**見出しの文言を変えると、ほかの文書からそこへのリンクが切れても気づけない**ので、見出しを変えたら `#見出し` で検索して直す。見出しからアンカーを作る規則が GitHub と違う描画（静的サイト生成）では「アンカー切れの検査を止めて」と頼む |
| 違反があったら | 指摘が Claude に返り、Claude がその場で直す。利用者の操作は要らない |
| 設定が無いプロジェクト | 何もしない。プラグインを全プロジェクトに入れても邪魔にならない |
| HTML の何を読むか | 本文の文字だけ。`script`・`style`・`pre`・`code` とタグの属性は読まない |
| 構造とアクセシビリティ | 画像の代替テキスト・見出しレベルの飛び・「こちら」だけのリンク・HTML の `lang` も見る。見出しの飛びは推奨の扱いで、意図して使っているなら「見出しの飛びの検査を止めて」と頼む |

### 5-1. 知見のまとめ

`manual-writer` は、構成（Diátaxis）・文章（Google / Microsoft）・日本語の表記（JTF・公用文作成の考え方）・Web での読まれ方（NN/g・GOV.UK）・アクセシビリティ（WCAG 2.2・デジタル庁）の要点を、出典つきのまとめとして読んでから書く。
**資料どうしで扱いが違う項目（長音・数字の全角半角・括弧内の句点）は、まとめではなく `voice.md` と用語集が決める。**
まとめの中身は Claude Code に「文書ハーネスの〇〇のまとめを見せて」と頼めば表示される。

検査項目の詳細は [check-docs 仕様](../reference/check-docs仕様.md) にある。

## 6. claude-dev-harness と併用するとき

| 文書 | 受け持つ側 |
|---|---|
| 利用者が読む文書（マニュアル・手順書・サイト・README） | 文書ハーネス（入口は `plan-doc`） |
| 設計書・機能設計書・レビュー記録・引き継ぎ（`docs/設計書/`・`docs/features/`・`docs/reviews/`・`docs/handoff/`） | harness-core（`update-docs` ほか） |

- 導入時に、harness-core が管理するフォルダは自動で検査対象から外れる
- harness-core の用語表（`.claude/rules/` の用語集）があれば、導入時に検査にも使うかを聞かれる。使うと用語表が1つにまとまる
- 実装を変えたら設計書は harness-core が更新する。**利用者向けの文書も変わる場合は、別に `plan-doc` に頼んで直す**（改訂の記録も残る）
