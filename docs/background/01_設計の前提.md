# 設計の前提

| 項目 | 内容 |
|---|---|
| 作成日 | 2026-10-02 |
| 対応ハーネス版 | harness-doc 0.1.0 |

**決定の記録であり、決定そのものは後から書き換えない。** 決定を変えるときは新しい文書を足す。

## 1. 何を解いているか

Claude Code が書くマニュアルは分かりにくい。原因は3つある。

1. **書き手の順に書く。** 読者がやりたいことの順ではなく、実装や機能一覧の順に並ぶ
2. **確かめずに書く。** 記憶と推測で書いたコマンドや画面名が、実物と食い違う
3. **曖昧語で済ませる。** 条件と値を調べる代わりに`必要に応じて`と書く

プログラムの品質をテスト・リンタ・CI で安定させるのと同じく、文書にも
**型（テンプレート）・手順（スキル）・自動チェック（フック）・レビュー（読者役）**を整備する。

## 2. 種類ごとに変えるのは3点だけ

アプリ操作・運用手順・仕様書で、進め方の大部分は共通である。種類ごとに変えるのは次の3点だけ。

| 変えるもの | 置き場 |
|---|---|
| 読者役が誰になりきるか | `profiles/`（beginner / operator / developer） |
| 見出し構成 | `templates/`（howto / reference / spec） |
| 検証方法（実行して確かめるか、コードと照合するか） | プロファイルの「検証方法」 |

スキルを種類ごとに分けると、共通部分の改善が全部に届かなくなる。だから**スキルは1本で、プロファイルを差し替える**。

## 3. 書く役とレビューする役を分ける

書いた本人は、文書に書いていないことを頭の中で補って読む。だから本人のレビューは
分かりにくさを検出できない。`doc-reviewer` は**文書以外の情報を持たない**前提で読み、
**書き換える権限を持たない**（`tools: Read, Grep, Glob`）。

レビューアーに書き手の懸念や結論を渡さないのも同じ理由による。渡すと追認になる。

## 4. 機械で止めるのは「兆候」だけ

分かりやすさは機械で判定できない。機械で止めるのは、分かりにくさの兆候
（曖昧語・言語指定の無いコードブロック・表記ゆれ・リンク切れ・見出しの欠落）に限る。
判定できないものは読者役レビューと手順の実行検証で補う。

## 5. プラグイン＋テンプレート層の2層

スキル・エージェント・フックはプラグインで配れる。`CLAUDE.md` の節と、プロジェクトごとに育てる
用語集・曖昧語リストはプラグインで配れない。どのみち2層が要るので、`claude-dev-harness` と同じ構成にした。

## 6. 設定不在は素通りする

`.claude/doc-harness.config.json` が無いプロジェクトでは、フックは何もしない。
プラグインを `--scope user` で入れると全プロジェクトでフックが走るため、
導入していないプロジェクトの作業を止めないことを優先した。
