# 読者プロファイル: operator（障害時に焦って読む運用担当）

## 読者像

- サービスを**運用**している。平常時の操作は知っているが、**障害は年に数回**で手順を覚えていない
- 読む状況: **深夜・障害中・焦っている**。上から順に読む余裕がなく、**結論から探す**
- コマンドラインは使える。ただし環境固有のパス・ホスト名は覚えていない
- 間違ったコマンドを打つと被害が広がることを知っている。**「このコマンドは安全か」を常に気にする**

## この読者が最もつまずく点

1. **結論が最後にある。** 背景説明を読み飛ばして、どのコマンドを打てばいいか探す
2. **コマンドがコピペで動かない。** プレースホルダ（`<host>`）が実値に置き換わっていない、
   カレントディレクトリが違う、権限が足りない
3. **期待される出力が無い。** 実行したが、これが正常なのか異常なのか分からない
4. **分岐が文章で書いてある。** 「もし A なら B、ただし C の場合は D」を焦って読み違える
5. **やってはいけないことが書いていない。** 再起動してよいのか、データが消えないか

## この読者向けの書き方の調整

- **結論と復旧コマンドを先頭に置く。** 「急ぐ人向け」の節を手順の前に作り、最短経路だけ書く
- **コマンドはコピペで動く形にする。** プレースホルダを使うなら、直前に「置き換える値の取り方」を書く
- **コマンドの直後に、期待される出力を必ず書く。** 正常時の出力と、異常時の出力の両方
- **分岐は表にする。** 「症状 | 原因 | 対処」。文章で分岐を書かない
- **破壊的な操作には警告を直前に置く。** 「このコマンドはキャッシュを消す。ユーザーデータは消えない」
- **所要時間と影響範囲を書く。** 「再起動中は約30秒、全ユーザーがアクセスできない」
- 連絡先・エスカレーション先を末尾に書く

## 検証方法

**手順を実際に実行して確かめる。** コードを読んだだけで「動くはず」と書かない。
本番で実行できない手順は、検証環境で実行し、本番との差（ホスト名・権限）を明記する。
実行できなかった手順は問い合わせに入れる。読者の判断に要るなら、本文には「検証環境では確かめていない（本番でだけ実行できる）」のように**事実として**書く（「未確認」の印ではなく）。

## レビュー時の観点

`doc-reviewer` はこの読者になりきって、次を点検する。

- 文書を開いて**30秒以内**に、最初に打つコマンドが分かるか
- コマンドをそのままコピペして動く形か（置き換えが必要な値は、取り方が書いてあるか）
- 各コマンドの期待される出力が書いてあるか。異常時の見分け方があるか
- 分岐が表になっているか
- 破壊的な操作に、直前の警告と影響範囲があるか
- 確かめていない手順が、どこまで確かめたかが分かる形で書かれているか（「検証環境では確かめていない」のように）
