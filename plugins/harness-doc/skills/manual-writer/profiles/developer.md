# 読者プロファイル: developer（保守・拡張する開発者）

## 読者像

- このコードを**書いていない**開発者。半年後の自分を含む
- 言語・フレームワークの一般知識はある。**このプロジェクト固有の判断・用語・制約は知らない**
- 読む状況: 機能を足す・バグを直す前に、**「どこを触ればよいか」「なぜこうなっているか」**を知りたい
- コードは自分で読める。**文書に求めるのは、コードに書いていないこと**（意図・制約・経緯）

## この読者が最もつまずく点

1. **文書とコードが食い違う。** 文書を信じて実装し、動かない。以後その文書を読まなくなる
2. **「なぜそうしたか」が無い。** 不自然な実装を「直して」しまい、避けていた問題を再発させる
3. **用語が揺れる。** 「ジョブ」「タスク」「バッチ」が同じものか別物か分からない
4. **制約が書いていない。** 「この API は1秒に10回まで」「この値は後方互換のため変えられない」
5. **コードで分かることが延々と書いてある。** 読む価値が無いと判断して閉じる

## この読者向けの書き方の調整

- **コードとの整合を最優先にする。** 書いた内容ごとに「確認した場所（パス・関数名）」を書く
- **「なぜそうしたか」を書く。** 選ばなかった案と、選ばなかった理由
- **用語を固定する。** 用語集に無い語は使わない。コード上の名前（クラス名・設定キー）と文書の語を対応させる
- **制約を明記する。** 変えてはいけない値・順序・互換性。「変えるとどうなるか」も書く
- **コードで分かることは書かない。** 関数の引数一覧を写さない。代わりにコードへリンクする
- 入口を書く。「この機能は `src/x/` から読む」「テストは `tests/x.test.ts`」

## 検証方法

**コードとテストと照合する。** 文書の各記述について、根拠になるファイルを `Read` / `Grep` で開く。
根拠が見つからない記述は「未確認」と書く。テストが無い振る舞いは、テストが無いことを書く。

## レビュー時の観点

`doc-reviewer` はこの読者になりきって、次を点検する。

- 各記述に「確認した場所」があるか。無い記述は推測ではないか
- 「なぜそうしたか」が、不自然に見える箇所に書いてあるか
- 用語が1つに固定されているか。コード上の名前と対応が取れるか
- 制約と、それを破ったときの結果が書いてあるか
- コードを読めば分かることを書いて、読む価値を下げていないか
