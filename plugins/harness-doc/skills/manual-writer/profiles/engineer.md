# 読者プロファイル: engineer（技術は持っているが、この製品は初めて）

## 読者像

- **専門の技術は持っている**（製品が扱う分野。例: 通信プロトコル・開発・試験・計測）。分野の用語（Modbus・TCP・エンディアン）は説明が要らない
- **この製品は初めて使う。** 製品の用語・画面構成・既定値は知らない。製品の用語が分野の用語と同じ字面だと、分野の意味で読む
- **自分の道具と組み合わせて使う**（手持ちのクライアント・テストコード・計測器）。文書の例と自分の道具の設定項目を突き合わせながら読む
- コマンドラインは使える。設定ファイルも読める
- 読む状況: 仕事の途中で、早く動かしたい。全部は読まず、必要な値（ポート・アドレス・形式）を探して拾い読みする

## この読者が最もつまずく点

1. **製品の用語と分野の用語が同じ字面。** 製品の「レジスタ」を Modbus の保持レジスタと取り違える
2. **自分の道具での書き方が分からない。** アドレスの数え方（0 から／1 から／5桁の書き方）、バイトとワードの並び（ABCD・CDAB）が、道具ごとに表記が違う
3. **うまくいかないとき、製品のせいか自分の設定のせいか切り分けられない。** 製品側の記録（ログ）でどう見えるかが書いていない
4. **既定値が書いていない。** ポート・周期・範囲を、画面を開いて探すことになる
5. **製品が対応していない方式を試して時間を失う**（例: 暗号化・別のフレーム形式）。対応範囲が書いていない

## この読者向けの書き方の調整

- **製品の用語は初出で定義し、分野の同じ字面の語と書き分ける。** 分野の側は「Modbus の保持レジスタ」のように分野の名前を付ける
- **相手の道具に入れる値を表にする。** 接続先・番号・機能・型・並びを、道具ごとの表記の違い（0 始まり・1 始まり・5桁）も含めて書く
- **製品側で見える確かめ方を書く。** 「通信ログに `FC04 読み取り 30001×2 OK` と出れば、製品は要求を受けて応答している」
- **症状 → 原因 → 対処を表にし、製品側と相手の道具側を見分けられるようにする**
- **既定値と対応範囲（対応しない方式）を書く。** 「3E フレーム・バイナリ・TCP だけ。4E・ASCII・UDP は対応しない」
- 分野の一般的な解説は書かない（読者は知っている。ブリーフの「扱わないこと」に入れることが多い）

## 検証方法

**実機で、相手の道具を使って通す。** 製品の画面だけで確かめず、相手の道具（クライアント・スクリプト）から読み書きして、書いた値で本当につながるかを確かめる。

- 相手の道具の設定（アドレスの数え方・並び）は、実際に読めた値と、わざと外したときの値の両方を確かめる（外したときの症状を、見分け方の表に書く）
- 製品の対応範囲は、設計書・ソースで確かめる。確かめられなければ問い合わせに入れる

## レビュー時の観点

`doc-reviewer` はこの読者になりきって、次を点検する。

- 製品の用語と分野の同じ字面の語を、取り違えずに読めるか（書き分けてあるか）
- 自分の道具に入れる値（接続先・アドレス・型・並び）が、道具ごとの表記の違いも含めて分かるか
- 読めない・つながらないとき、製品側か自分の側かを切り分ける手がかり（製品のログ・状態の表示）があるか
- 既定値と対応範囲が書いてあるか
- 分野の一般的な解説で、必要な値が埋もれていないか
