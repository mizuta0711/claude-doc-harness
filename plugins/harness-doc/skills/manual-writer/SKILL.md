# manual-writer

文書を**熟練テクニカルライターと同じ進め方**で書くスキル。進め方は文書の種類によらず共通で、
種類ごとに変えるのは**読者プロファイル・テンプレート・検証方法の3点だけ**。

> **何を解いているか。** AI が書くマニュアルは「書き手が知っていることを、書き手の順に、
> 曖昧な語で」書くので分かりにくい。読者を先に決め、事実を実物で確かめ、
> 予備知識のない読者役に読ませ、機械で曖昧語を止める。この4つで水準を揃える。

**入口は `/harness-doc:plan-doc`。** plan-doc が依頼の性質と規模（S/M/L）を判定し、M・L の新規作成・改訂・誤りの修正をこのスキルに渡す。
**利用者からこのスキルを直接頼まれたら、先に `/harness-doc:plan-doc` の受付と規模判定を通す**（小さな修正なら、plan-doc の中で短い経路で終わる）。
plan-doc から渡されたときは、承認済みの規模と前提を受け取っているので、Step 1 で同じ問いを繰り返さない。

## 種類ごとに差し替えるもの

| 種類 | テンプレート | 読者プロファイル | 検証方法 |
|---|---|---|---|
| 手順書（操作・運用・復旧） | [templates/howto.md](templates/howto.md) | beginner または operator | **手順を実際に実行して**結果を確かめる |
| リファレンス（設定・コマンド・API） | [templates/reference.md](templates/reference.md) | developer または operator | **コード・設定と照合**する |
| 仕様書（振る舞い・制約） | [templates/spec.md](templates/spec.md) | developer | **コード・テストと照合**する |

読者プロファイルは3つ。迷ったら「読み終えたら何ができるべきか」で選ぶ。

| プロファイル | 読者像 | ファイル |
|---|---|---|
| beginner | 初めて使う人。画面を見ながら読む | [profiles/beginner.md](profiles/beginner.md) |
| operator | 障害時に焦って読む運用担当 | [profiles/operator.md](profiles/operator.md) |
| developer | 保守・拡張する開発者 | [profiles/developer.md](profiles/developer.md) |

良い例と悪い例は [examples/good.md](examples/good.md) と [examples/bad.md](examples/bad.md) にある。

## 知見のまとめ（出典つき）

文書の構成・文章・表記・Web での読まれ方・アクセシビリティの定番の知見を、出典を確かめてまとめてある。
**記憶で書かず、ここを読んでから書く。** `Read` で開かず、次のコマンドで出力して読む（プラグインはプロジェクトの外にあるため）。

```bash
node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" reference <名前>
```

| 名前 | 中身 | 読む Step |
|---|---|---|
| `structure` | 文書の4種類（チュートリアル・手順書・リファレンス・解説）と見分け方（Diátaxis） | Step 3 |
| `web` | 拾い読みされる前提の書き方、結論を先に、見出しと段落（NN/g・GOV.UK） | Step 3・4 |
| `writing` | 手順・見出し・リスト・表・UI・コード・リンク・画像・注記の書き方（Google・Microsoft） | Step 4 |
| `japanese` | 文体・表記・数字・記号・文の長さ・用語（JTF・公用文作成の考え方） | Step 4 |
| `accessibility` | 代替テキスト・色・見出し・リンク・言語・表（WCAG 2.2・デジタル庁） | Step 4（画像・HTML を書くとき） |

**資料どうしで扱いが違う項目**（長音・数字の全角半角・括弧内の句点）は、リファレンスではなくプロジェクトの `voice.md` と用語集に従う。
**書く前に両方読む。** 悪い例には「なぜ悪いか」が付いている。

## Step 0: プロジェクトに導入済みかを確かめる

プロジェクトのルートに `.claude/doc-harness.config.json` があるかを確かめる。

- **ある**: `docs-style/voice.md` も見る。`<!-- status: 未設定 -->` のままなら、文体が決まっていない。
  「先に文体を決めますか」と聞き、はいなら `/harness-doc:setup-project` の文体の部分（既存なら読み取り、新規なら見本から選択）を行う。
  いいえなら、文体の見本集（`node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" voices`）の B（標準の敬体）で書き、完了報告にそう書く。Step 1 へ進む
- **無い**: このままでは `check-docs` フックが動かず、用語集も無い。利用者に「このプロジェクトに
  文書ハーネスを導入してから書く」ことを1行で伝えて了承を得たら、`/harness-doc:setup-project` を
  実行してから Step 1 へ進む。断られたら、フックと用語集なしで書くことを完了報告に明記する

書く文書が config の `exclude` に当たる場合（claude-dev-harness の `docs/設計書/`・`docs/features/`・`docs/reviews/`・`docs/handoff/`）は、このスキルの対象外。
その旨を伝え、harness-core のスキル（`update-docs` ほか）に任せる。

## Step 1: 読者とゴールを決める

**一度決めた読者・範囲は、ブリーフ（文書群ごとの決め事）に残っている。毎回まっさらから決め直さない。**
書く文書のパス（新規ならこれから作るパス）で、ブリーフを引く。

```bash
node "${CLAUDE_SKILL_DIR}/../../scripts/brief.mjs" show <文書のパス>
node "${CLAUDE_SKILL_DIR}/../../scripts/brief.mjs" missing <文書のパス>
```

> 既存の文書を `Read` すると、ブリーフの中身はシステムから自動で差し込まれる。ただし**新規作成（`Write`）では差し込まれない**ので、
> 新規・既存によらず、書く前に上のコマンドで引く。

1. **埋まっている項目は聞かない。ただし黙って進まず、前提を1行で示す。**

   ```text
   この前提で書きます: 読者 = 初めて使うシニア（文書群「利用者向けの使い方」） ／ 扱わないこと = 端末 OS の設定
   ```

2. **文書ごとの「ゴール」「文書の種類」だけが欠けているなら、聞かない。** 依頼文から案を作って `"by":"書き手"`（仮定）で書き、前提の1行に含める。目次案（Step 3）の確認で一緒に確かめてもらう（問いを1回増やさない）
3. **それ以外で `missing` が挙げた「欠けている項目」と「仮定」の項目だけを、まとめて1回で聞く**（`AskUserQuestion` は1回4問まで。書き手が答えの案を出し、依頼者は承認か修正をするだけにする）。
   依頼が、ブリーフの「扱わないこと」と食い違うときは、同じ問いで一言添える（「前回、〇〇は扱わないと決めています。今回は扱いますか」）
4. 答えをブリーフに書く。**`.claude/` 配下は `Edit` で書かず、次のスクリプトで書く**（依頼者が決めた値は `"by":"依頼者"`、書き手が置いた仮定は `"by":"書き手"`）

   ```bash
   node "${CLAUDE_SKILL_DIR}/../setup-project/scripts/apply.mjs" --brief '{"name":"usage","by":"依頼者","set":{"文書ごとの決め事":{"phone.html":{"ゴール":"発信して通話を終えられる","文書の種類":"手順書","受け入れ基準":"1. 文書だけで発信できる 2. 通話を切れる"}}}}'
   ```

   文書ごとの決め事の見出しは、ブリーフの `paths` の基点からの相対パス（`show` が「文書ごとの見出し」として出す）
5. ブリーフが無い（`show` が「無い」と言う）場所の文書なら、新しい文書群を作る。**ただし、プロジェクトにブリーフが1つも無い（`brief.mjs list` が空）なら、0.6.0 以前に導入したプロジェクトなので、先に `/harness-doc:setup-project` の「導入済みのプロジェクトに足す」を1行で勧める（文書群をまとめて決めた方が、あとで重ならない）。断られたら、この文書の文書群だけを作る。**名前（英数字）・文書群の名前・`paths` の案を示し、上の問いと同じ1回で承認をもらってから、`title` と `paths` を付けて書く

次を **1〜2文**で書き、以後の Step で使う。

> 誰が、どんな状況で読み、読み終えたら何ができるようになるべきか。

- 確認できない場合は仮定を置き、**ブリーフに「仮定」で書く。本文には書かない**（読者に「仮定」を見せても役に立たない。完了報告で依頼者に確かめてもらう）
- **既存の文書を直すなら、これまでの経緯を読む。** 内部の改訂記録から、その文書の節を新しい順に出す

  ```bash
  node "${CLAUDE_SKILL_DIR}/../../scripts/history.mjs" show <文書のパス>
  ```

  前の改訂意図と「見送ったこと・決めたこと」に反する直し方をしない。反するなら、それを依頼者に確かめる（完了前の問いにまとめる）。
  **記録は読者役に渡さない**（書き手の意図が書いてあり、渡すと追認になる）
- 上の表から最も近いプロファイルを選び、`node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" profile <名前>` で出力して読む
  （`Read` で開くと、プロジェクトの外なので権限の確認が出ることがある）。選んだ理由を1行で記録する
- **`docs-style/voice.md` を読む。** 文体（文末・温度・専門用語・一文の長さ）と見た目（HTML なら従う CSS・図の描き方）は
  ここに従う。読者プロファイルは「誰が読むか」、voice.md は「どう語りかけ、どう見せるか」で、両方に従う
- 既存文書の書き換えなら、**今の文書の読者とゴールも書き出す**。ずれていればそれが書き換えの軸になる

**この Step を飛ばして本文を書かない。** 読者が決まっていない文書は、誰にも刺さらない。

## Step 2: 事実を確認する

**記憶や推測で書かない。** 対象を実物で確かめる。

| 書くこと | 確かめ方 |
|---|---|
| コマンドと出力 | **実際に実行する**（`Bash`）。出力をそのまま文書に写す |
| 画面名・ボタン名・メニュー名 | UI の文字列リソース・スクリーンショット・実機で確認し、**表記を完全に一致させる** |
| 設定項目・既定値 | 設定ファイル・コードを `Read` / `Grep` で読む |
| 振る舞い・制約 | コードとテストを読む。テストが無い振る舞いは問い合わせの候補 |
| 既存文書の記述 | そのまま信じない。上の方法で確かめ直す |

確かめられなかった事実は、**断定しない。ただし本文に「未確認」とも書かない**（「未確認」は書き手と依頼者のあいだの印で、読者には不安を与えるだけ）。

| | 書き方 |
|---|---|
| 本文のその箇所 | 読者にとって正しい書き方にする（「端末によって違います。端末の説明書を見てください」）。書けなければ、その箇所を書かない。**箇所に `<!-- 問い合わせ: Q1 -->` の印を置く**（中身は番号だけ。HTML のソースは公開されるため） |
| 完了報告 | 「問い合わせ」の行に、番号・確かめられなかった事実・何で確かめようとしたかを書く。依頼者の回答で解消したら、印を消して本文を直す |

**仕様書（`spec`）は例外。** 開発者の読者には未確認・未決の事項を伝えるのが正しいので、テンプレートの「未確認・未決事項」の節に書く（本文の途中には書かない）。

**仕様と実装が食い違ったら、書き手がどちらかに寄せない。** 製品の振る舞いが不具合に見えるとき（「連絡先から発信しても権限を聞かない」）、回避策を書いて埋めない。
その箇所は書かずに問い合わせに入れ、完了報告の問いで依頼者に選んでもらう（文書を今の振る舞いに合わせる／製品を直すまで書かない／暫定の回避策として書き、見直す条件を書く）。

実行できない手順（本番環境の操作・権限が要る操作）は、**実行できなかったこと**と
**代わりに何で確かめたか**（コード・過去の記録・担当者の証言）を記録する。

### 実行する前に止まる操作

確かめるための実行で、環境を壊したり、他人に影響を与えたりしない。次に当たるコマンドは、**実行する前に依頼者に確かめる**（何を・どの環境で実行するかを1行で示す）。

| 止まる操作 | 例 |
|---|---|
| 削除・上書き・初期化 | `rm`・`DROP`・`TRUNCATE`・`git reset --hard`・`--force` の付いた操作・データの初期化 |
| サービスの停止・再起動 | `systemctl restart`・`docker compose down`・アプリの再起動 |
| 本番環境・共有環境への接続 | 接続先が本番か共有か分からないときも含む |
| 外部への送信 | メール・通知・課金・外部 API への書き込み |

確かめられないまま実行しない。断られたら、上の「実行できない手順」と同じように扱う。

### 出力を写すときに伏せるもの

「出力をそのまま写す」は、**伏せるべきものを伏せてから写す**という意味である。次は例に置き換える（例に使う値は `voice.md` に決まっていればそれに従う）。

| 伏せるもの | 置き換えの例 |
|---|---|
| トークン・パスワード・API キー・秘密鍵（一部でも） | `<トークン>` |
| 実名の入ったパス（`C:\Users\<実名>`・`/home/<実名>`） | `C:\Users\<ユーザー名>` |
| 内部のホスト名・IP アドレス・社内 URL | `example.com`・`192.0.2.10`（文書用に予約された値） |
| 個人の名前・メールアドレス・電話番号 | `user@example.com`・`090-0000-0000` |

置き換えたことで読者の操作が変わる値（読者が自分の環境の値を入れる箇所）は、「`<ユーザー名>` は自分のユーザー名に置き換える」と本文に書く。

## Step 3: 目次案を作る

テンプレートをベースに、見出しを並べる。先に `structure` と `web` のリファレンスを読む。

- **この文書の種類を1つに決める**（チュートリアル・手順書・リファレンス・解説）。2つの種類にまたがるなら分割し、もう一方へはリンクで渡す
- **「読者がやりたいこと」の順に並べる。** 実装の都合・機能の一覧順にしない
- **結論を先に置く。** 冒頭の2段落以内で、読者が知るべきこと・すべきことが分かるようにする
- 見出しは内容を表す語にし、大事な語を先頭に置く。「はじめに」「概要」「その他」だけの見出しにしない
- operator 向けは**結論と復旧コマンドを先頭**に置く（プロファイル参照）
- 冒頭の `<!-- doc-type: ... -->` マーカーは消さない。`check-docs` が必須見出しの判定に使う
- **受け入れ基準の案を作る。** 「読者が文書だけで〇〇できる」を3〜5個。読者役はこれで合否を判定する（Step 6）。
  ゴール・文書の種類がブリーフに無ければ、それも案を作る（Step 1 では聞いていない）
- **目次案と受け入れ基準の案を一緒に依頼者に見せ、返事を待つ。** 本文を書いてからの構成変更は高くつく。
  「この目次で進めて」で本文へ、並びや基準の指摘があれば作り直す。依頼文で「目次の確認は要らない」「任せる」と言われていれば待たない。
  承認された受け入れ基準・ゴール・文書の種類は、ブリーフの文書ごとの決め事に `"by":"依頼者"` で書く（`apply.mjs --brief`）。
  「任せる」と言われて確認を省いたときは、`"by":"書き手"`（仮定）で書き、完了前の確認で確かめる

## Step 4: 本文を書く

### 書き方の規則

1. 冒頭に「この文書で何ができるようになるか」を書く
2. **1つの手順に、1つの操作だけ**を書く
3. 手順は番号付きにする
4. コマンドはコードブロックに入れ、**言語指定**を付ける（`bash` / `powershell` / `text` / `json`）
5. コマンドの**直後に、期待される出力または画面の状態**を書く
6. 専門用語は初出で説明する。説明できない用語は使わない
7. 画面名やボタン名は UI の表記と完全に一致させる（「保存ボタン」ではなく「**保存**」ボタン）。
   **囲み方（太字か「」か）は `voice.md` の「表記」に決まっていればそちらに従う**（既存のサイトの書き方を踏襲する。この規則の太字は、決まっていないときの既定）
8. 曖昧語を使わない。`banned-words.txt` にある語（`適宜`・`しばらく`・`必要に応じて`）は
   **条件と値**に置き換える。例: `しばらく待つ` →「`Ready` と表示されるまで待つ（30秒以内）」。
   **語そのものを説明するときは、コードとして囲む**（Markdown は `` `適宜` ``、HTML は `<code>適宜</code>`）。囲まないとフックが止める
9. 失敗しやすい箇所には、**「うまくいかない場合」を直後に置く**（文末にまとめて追いやらない）
10. 前提条件（環境・権限・事前準備）を、手順の**前**にまとめて書く
11. 用語は `docs-style/glossary.md`（と config の `glossaryFiles`）に揃える。新しい用語が要るとき・推奨表記を変えたいときは、
    **用語集に足す前に依頼者に確かめる**（書き手が一人で決めた語が用語集の正にならないように）。完了報告の「書き戻し」の問いにまとめてよい。
    専門用語を言い換えたときは、旧称を本文に1回併記する（「電源を入れ直す（再起動）」）。検索で見つかるように
12. **文体は `docs-style/voice.md` の見本の文に合わせる。** HTML は「従う CSS」の既存のクラスと部品を使い、新しい見た目を作らない
13. 手順の各ステップは**場所 → 操作 → 結果**の順に書く（「**設定** 画面で **保存** を選ぶ。『保存しました』と表示される」）。
    省略できるステップは行頭に「任意:」と書く（`writing` リファレンス §2）
14. リンクの文言は行き先を表す語にする。「こちら」「ここ」だけにしない（`accessibility` 要点 12）
15. 画像には内容を説明する代替テキストを付ける（80字が目安）。飾りの画像は空にする（`accessibility` 要点 1〜4）
16. 対象を「右の」「丸い」「緑の」だけで指さない。ボタン名を併記する（`accessibility` 要点 9）
17. 例示の語（`など`）を使うときは、その前に代表例を挙げる（`japanese` §5）

### 書かないこと

- 「簡単に」「すぐに」「便利な」のような評価語。読者が判断する
- 「〜と思います」「〜かもしれません」。確かめて断定するか、問い合わせに入れる（Step 2）
- 読者が知らなくてよい内部事情（実装の経緯・開発者の苦労）

## Step 5: 自己点検する

本文を書き終えたら、次を**1つずつ実物で確認**してチェックを付ける。

- [ ] 読者とゴールが冒頭に明記されている（仮定はブリーフにだけ書き、本文には書かない）
- [ ] 前提条件がすべて書かれている（環境・権限・事前準備）
- [ ] 各手順の結果を確認する方法が書かれている
- [ ] 用語が `docs-style/glossary.md` と一致している
- [ ] **実行したコマンドと、書いたコマンドが一致している**（コピーし直して比べる）
- [ ] 写した出力・画像から、トークン・実名の入ったパス・内部のホスト名・個人情報を伏せた（Step 2「出力を写すときに伏せるもの」）
- [ ] 確認できていない事実は断定せず、本文には「未確認」と書かずに問い合わせの印（番号だけ）を置いた（仕様書は「未確認・未決事項」の節）
- [ ] 選んだプロファイルの「レビュー時の観点」を自分で当てた

## Step 6: `doc-reviewer` でレビューし、指摘を反映する

`doc-reviewer` エージェントを **`Agent` ツールで起動**する。プロンプトには**必ず**次を含める。

- 文書の**絶対パス**
- 選んだ**読者プロファイル名と、その内容**（Step 1 で出力したものを貼る）と、Step 1 で書いた読者とゴールの1〜2文
- **ブリーフ**（`brief.mjs show` の出力を貼る）。読者役は「扱わないこと」に当たる指摘を致命的にしない。読者役が文書を `Read` したときにも自動で差し込まれるが、それに頼り切らない
- `docs-style/voice.md` の**絶対パス**（文体が合っているかも点検してもらう）
- 「**文書以外の情報（この会話の経緯・書き手の意図）は知らない前提で読むこと**」
- 「**ブリーフの受け入れ基準を、判定に使うこと。** 基準ごとに満たす／満たさない／判定できないを返し、基準を満たせない原因になっている指摘を致命的にすること」

**レビューアーには自分の懸念や結論を渡さない。** 渡すと追認になる。**内部の改訂記録・改訂意図も渡さない。**

### 指摘の扱い（読者役は意図を知らずに読み、このスキルが意図と照らして決める）

| 指摘の種類 | 扱い |
|---|---|
| 受け入れ基準を満たせない原因になっている | 致命的。直す |
| 基準には関係しないが、読者が詰まる | 要修正。直すか、見送りの理由を書く |
| ブリーフの「扱わないこと」に当たる | 範囲外の提案。致命的にしない |
| それ以外 | 提案 |

返ってきた指摘は**全件**に「対応済み」か「見送り（理由）」を付けて本文へ反映する。見送りは、**読者ではなく書き手の都合**で決めていないかを疑う。

- 改訂意図や過去の決定を理由に見送るときは、**どの意図によるかを書く**（「見送り: 2026-10-05 の改訂意図『端末 OS は扱わない』による」）。理由を書けない見送りは認めない
- **同じ箇所への指摘が、意図を理由に2回見送られたら、意図そのものを疑う。** 読者に伝わっていない兆候なので、完了前の問いで「意図を保つか、変えるか」を依頼者に聞く
- 見送った指摘とその理由は、内部の改訂記録の「見送ったこと・決めたこと」に残す（完了処理で書く）

### 終える条件

1. 受け入れ基準をすべて満たし、致命的が0なら終える
2. 1回目で致命的・要修正が0なら、2回目は要らない
3. 直したら、**新しい `doc-reviewer`** でもう1回レビューする。1回目の指摘も対応の内容も渡さない（追認を避ける）
4. **2回まわしても基準を満たさなければ、3回目をまわさず、依頼者に判断を渡す。** 選択肢は「基準を直す」「範囲外とする」「もう1回まわす」。
   この問いは、その場で聞かずに完了前の問い（完了報告）にまとめる

> レビューアーは文書を**書き換えない**（読む役と書く役の分離）。書き換えるのはこのスキル。

## Step 7: フックの機械チェックを通す

文書（`.md` / `.html`）を書くたびに `check-docs` フックが走る。HTML では本文のテキストとリンクを検査し、`<code>`・`<pre>` の中は読まない。失敗したら指摘を直す。

Write / Edit 以外（Bash のヒアドキュメントや sed）で書いた場合はフックが走らないので、
プロジェクトのルートで次を実行して確かめる（`${CLAUDE_SKILL_DIR}` は絶対パスに置き換えて書く）。

```bash
node "${CLAUDE_SKILL_DIR}/../../hooks/scripts/check-docs.mjs" docs/guide/対象.md
```

`[check-docs] OK: ...` と出れば通過。検査の抑止（`<!-- check-docs: skip -->`）は
**理由をその行に書ける場合だけ**使う。

## 完了前の確認（1回）

**記録を書く前に、ためておいた問いを1回だけ聞く**（完了報告の案を示し、同じ問いで）: 問い合わせ・仕様と実装の食い違いの扱い・
読者役が2回で基準を満たさなかったときの判断・意図を理由に2回見送った指摘・書き戻し（下の「決まったことを次に生かす」）・用語の追加。
**答えを本文とブリーフに反映してから、記録を書く**（記録は追記だけで、書いた節は後から直さない）。どれも無ければ聞かない。

## 改訂の記録と完了処理

**改訂の記録は必ず残す。** 新規作成も、既存の文書の改訂も同じ。「変更者・承認者」は、完了前の確認で承認をもらった人を書く。

1. **内部の改訂記録に1節を足す**（必須）。改訂箇所・改訂内容・**改訂意図**（空にしない）・根拠・見送ったこと（読者役の指摘を意図を理由に見送ったものを含む）を書く

   ```bash
   node "${CLAUDE_SKILL_DIR}/../../scripts/history.mjs" add --json '{"doc":"docs/usage/phone.md","size":"M","改訂箇所":"手順1〜4・うまくいかない場合","改訂内容":"権限の説明を手順の前に移し、通話の切り方を足した","改訂意図":"初めて使う読者が、発信の前に許可の画面で止まらないように","根拠":"MainActivity.kt:168-181","見送ったこと・決めたこと":"機内モードの解除は扱わない（ブリーフの扱わないこと。読者役の指摘を見送り）","読者向けの改訂履歴":"手順1：電話の許可の説明を手順の前に移しました","変更者・承認者":"Claude・依頼者","改訂設計書":"なし（P2a の暫定）"}'
   ```

2. ブリーフで**読者向けの改訂履歴が「あり」**なら、文書の「改訂履歴」の節に1行足す。いつ・どこを・どう変えたかを、読者向けの言葉で簡潔に（改訂意図や根拠は書かない）。
   新規作成なら「初版」の1行
3. **完了処理の検査を通す。** `NG` が出たら直す。問い合わせの印を残したまま渡すなら `--allow-queries` を付け、完了報告にそう書く

   ```bash
   node "${CLAUDE_SKILL_DIR}/../../scripts/complete-doc.mjs" <書いた文書のパス>
   ```

## 完了報告

次を報告して終わる。

| 項目 | 内容 |
|---|---|
| 文書 | パス |
| 読者とゴール | Step 1 の1〜2文。仮定ならそう書く |
| プロファイル | 選んだもの |
| 事実確認 | 実行したコマンドの数、照合したファイル |
| **問い合わせ** | 確かめられなかった事実を全部（番号・内容・何で確かめようとしたか）。仕様と実装の食い違いもここ。無ければ「なし」。**依頼者が確かめるものなので、行を省かない** |
| 読者役レビュー | 回数。受け入れ基準ごとの判定。指摘の件数（致命的／要修正／提案）。**見送った指摘は1件ずつ、内容と理由**（意図を理由にしたなら、どの意図か） |
| 誤っていた指摘 | 読者役の指摘のうち、実物で確かめて誤りだったもの（読者役の精度を測る材料） |
| 文書の外で見つかった問題 | 製品の不具合・ほかの文書の誤り（あれば） |
| 改訂の記録 | 内部の改訂記録に足した節・読者向けの改訂履歴に書いた1行 |
| 完了処理の検査 | `complete-doc.mjs` の結果 |
| 機械チェック | 通過したか |
| ブリーフ・設定 | 書いた・変えた項目（ブリーフ・`voice.md`・用語集・config） |
| 依頼者が次にやること | 問い合わせへの回答・技術査読を頼みたい箇所（業務の決まり・運用の慣習のように、システムを知る人でないと正誤が分からない記述）・入口（目次やサイドバー）への登録・公開の操作 |
| ハーネスへの還元候補 | 作業中に見つかった曖昧語・用語・型の改善（あれば） |

完了報告は、完了前の確認の答えを反映し、記録と検査を済ませた後に出す。**ここでは新しく問わない。**

還元候補は**その場でハーネスを直さず**、依頼者に伝える。まとめて直す方が質が上がる。

### 決まったことを次に生かす（書き戻し）

依頼者が作業中に「ここは書かなくていい」「この言い方はやめて」「覚えておいて」と言ったことは、次の文書でも効くように書き戻す。
完了前の確認と同じ問いで、**1問だけ**聞く（選択肢は「全部」「選ぶ」「しない」）。

```text
今回の作業で決まったことのうち、次の文書にも効きそうなもの:
  1. 端末 OS の設定は扱わない → ブリーフの「扱わないこと」へ
  2. UI 名は「」で囲む → voice.md の「表記」へ
  3. 用語「キーパッド」を「数字のボタン」に言い換える → 用語集へ
書き戻しますか
```

候補は会話から拾う。**依頼者が「覚えておいて」と言ったことは必ず候補に入れる。** 候補が無ければ聞かない。
ブリーフへは `apply.mjs --brief`、`voice.md` と用語集へは `Edit` で書く。
