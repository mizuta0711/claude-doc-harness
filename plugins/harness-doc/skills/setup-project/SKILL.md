# setup-project

今のプロジェクトに文書ハーネスを**対話で**導入する。**利用者にコマンドを打たせない。**
決めることは利用者に聞き、それ以外（ファイルを置く・設定を書く）はすべてこのスキルの中で行う。

> **なぜ対話にするか。** 文書の置き場所・文体・見た目はプロジェクトごとに違い、ハーネスの既定値を
> 押し付けると既存の文書と食い違う（実例: 用語集の初期値 `サーバー` が、`サーバ` で統一していた
> プロジェクトの51か所を止めた）。**既存のものは踏襲し、決まっていないものだけ選んでもらう。**

使うスクリプトと資料（`${CLAUDE_SKILL_DIR}` は絶対パスに置き換えて書く。シェル変数ではない）:

| 名前 | パス | 役割 |
|---|---|---|
| 棚卸し | `${CLAUDE_SKILL_DIR}/scripts/inventory.mjs` | 文書の置き場所・用語表・CSS を調べる（読むだけ） |
| 適用 | `${CLAUDE_SKILL_DIR}/scripts/apply.mjs` | 雛形を置く（既存ファイルは上書きしない） |
| 文体の見本集 | `node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" voices` | 新規のとき見せる |
| 見た目の方向性 | `node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" visuals` | 新規の HTML サイトのとき見せる |

資料は `Read` で開かず、`node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" voices`（または `visuals`）で出力して読む。
プラグインはプロジェクトの外に置かれ、`Read` だと権限の確認が出たり拒否されたりするため。

## 質問のしかた

- **`AskUserQuestion` ツールで選択肢として聞く。** 使えない環境では、番号付きの選択肢を文章で示して答えを待つ
- **1回の問いかけで聞くのは4問まで。** 関連する問いはまとめる
- **推奨の選択肢を先頭に置き、「（推奨）」と付ける。** 推奨の根拠（既存の文書から読み取った事実）を説明に書く。**依頼者だけが知っている事実（配布先・接続先・社内の決まり）を聞く問いには推奨を付けない**（`node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" path questions` の 1）
- 文体は**見本の文**を見せて選んでもらう。項目名だけでは選べない
- **既に決まっていること（既存の文書から明らかなこと）は聞かない。** 読み取った結果として示し、違っていれば直してもらう
- **承認を求める案（ブリーフの表・用語集に足す語・置き場所）は、問いの本文か直前の出力に全部書く。** 考えた中にだけ置いて「この案でよいか」と聞かない（依頼者からは見えない。実地検証で起きた）
- **書き手が案を作ったものは、黙って適用しない。** 用語集に足す語・ブリーフの値・検査に入れる文書は、どれも問いに載せて承認か修正をもらう。問いの回数を増やさないよう、Step 2C の1回にまとめてよい

## Step 1: 棚卸しする

```bash
node "${CLAUDE_SKILL_DIR}/scripts/inventory.mjs" --dest "<導入先>"
```

導入先は $ARGUMENTS のパス、無ければ今のプロジェクトのルート。

| 結果 | 次 |
|---|---|
| `hasHarnessDoc: true` | 導入済み。**導入をやり直さない。** 次のどれかに当たれば、**「導入済みのプロジェクトに足す」**（下の節）を行う。(1) ブリーフ（`.claude/rules/doc-brief-*.md`）が1つも無い（`node "${CLAUDE_SKILL_DIR}/../../scripts/brief.mjs" list`）。(2) `CLAUDE.md` の「文書ルール（harness-doc）」の節が最新版（`node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" claude-section`）と違う。(3) ブリーフの文書群に、内部の改訂記録（`docs-style/history/<名前>.md`）が無い。どれにも当たらなければ、文体を変えたいなら `plan-doc`（テイスト変更）、読者や範囲を変えたいなら `plan-doc`（方針変更として `change-policy` に渡る）を案内して終える |
| `existing: true`（利用者向けの文書の候補がある） | Step 2A（既存） |
| `existing: false` | Step 2B（新規） |

判定に迷う場合（候補が README だけ）は、「既存の文書を踏襲しますか、新しく決めますか」と1問聞く。

## Step 2A: 既存 — 読み取って踏襲する

### 2A-1. 検査する文書の置き場所を決める

`candidates`（利用者向けの文書の候補）を**複数選択**で聞く。`docDirs` の数を説明に添える。

- 候補にはアプリの画面（`web-ui/public` のような）や開発文書も混ざりうる。**決めつけずに選んでもらう**
- `managedByDevHarness: true` の場所（dev-harness の設計書・機能設計書・レビュー記録・引き継ぎ）は候補に出さない（自動で対象外）
- 選ばれた場所から `include` を作る（`<場所>/**/*.md`・`<場所>/**/*.html`。その場所にある拡張子だけ）
- `README.md` があれば、候補に「`README.md`（推奨）」として並べる（入れると文書群 `default` になる）。黙って入れたり外したりしない

### 2A-2. 今の文体を読み取る

選ばれた場所から、**文書の種類ごとに2〜3本**を読む（全部は読まない）。次を数えて読み取る。

| 項目 | 読み取り方 |
|---|---|
| 文末 | 句点で終わる文の、敬体（です・ます）と常体（だ・である）の割合 |
| 語りかけの温度 | 「〜してください」「〜しましょう」の有無、感嘆符、やわらかい言い回し |
| 専門用語 | 説明なしで使っている専門語の多さ |
| 一文の長さ | 句点までの字数のおおよその中央値 |
| 表記の好み | 長音（`サーバ` / `サーバー`）・送り仮名・数字（全角/半角）・括弧・操作の動詞（押す / タップ / クリック）・画面のたどり方・コードやファイル名の囲み方。**多数派を正とする** |
| 見本の文 | 実物から、その文書らしさがよく出ている文を2〜3文引用する |

**場所ごとに文体が違う**ことがある（例: 利用者向けは敬体、リファレンスは常体）。違っていれば、多い方を `voice.md` に書き、
もう一方はその場所の文書群のブリーフの「文体の差分」に書く（Step 2C）。`voice.endings` は `null`（機械では検査しない）にする。

### 2A-3. 読み取った結果を確かめてもらう

読み取った文体を表と見本の文で示し、1問で聞く。

- 「このまま踏襲する（推奨）」/「一部を変える」/「見本集から選び直す」
- 「一部を変える」なら、変えたい項目を続けて聞く
- 「選び直す」なら Step 2B-1 の質問をする

### 2A-4. 用語表と見た目

- `termFiles` があれば、「この用語表を検査にも使いますか（推奨: はい）」と聞く。はいなら `glossaryFiles` に入れる。
  **このとき `docs-style/glossary.md` は空のまま置き、二重に管理しない**
- 表記の好み（長音・送り仮名・数字）で多数派がはっきりしたものは、`docs-style/glossary.md` に足す案を示して確かめる。
  **足すのは承認された語だけ。** 文書で見かけた言い回し（「長く押す」）を、書き手の判断で推奨表記にしない（用語集は検査の正になり、外れた書き方を全部止める）。確かめるのは Step 2C の1回にまとめてよい
- HTML の場所を選んだ場合、`cssFiles` から**その場所が読み込んでいる CSS**（HTML の `<link>` を見る）を特定し、
  `voice.md` の「従う CSS」に書く。**既存の見た目は変えないので、聞かない**
- 図の描き方（スクリーンショット・CSS のモック・CSS の図部品）は実物から読み取って書く
- **既存の文書に改訂履歴の節があれば、その見出しの名前を読み取る**（「更新履歴」「変更履歴」のように「改訂履歴」と違うなら、
  config の `revisionHeadings` に書く。完了処理の検査がその名前で節を探す）。`apply.mjs --config '{"revisionHeadings":["更新履歴"]}'`
- **2A-2 で読んだ文書の見出しを、必須見出し（`requiredHeadings`）と比べる。** 手順書なら「できること・前提条件・手順・確認・うまくいかない場合」、リファレンスなら「一覧」、仕様書なら「目的・用語・仕様・制約・未確認」。
  同じ役目の節が違う語で揃っているなら（「前提条件」の代わりにどの手順書も「準備」）、その種類の見出しを既存の語に置き換える案を示し、Step 2C の問いで一緒に確かめる。
  承認されたら `apply.mjs --config '{"requiredHeadings":{"howto":["できること","準備","手順","確認","うまくいかない場合"]}}'`（種類ごとに置き換わり、ほかの種類は既定のまま）。
  既定の語のまま導入すると、次に新しく書く文書が既存のサイトと違う見出しになるか、`check-docs` に止められる（実地検証で、既定の語が既存のサイトと衝突した）。
  役目の節そのものが無い（手順書に前提の節が無い）のは語の違いではないので、合わせない。既存の文書に `doc-type` のマーカーは付けない（導入では文書を書き換えない。付けるのは、その文書を plan-doc で直すとき）

## Step 2B: 新規 — 見本から選んでもらう

### 2B-1. 文体を選ぶ

文体の見本集（`show.mjs voices`）の A〜D を、**各見本の文を説明に入れて**選択肢として出す。読者の想定を先に聞いた方が選びやすければ、
「主な読者」（初めての人・一般の利用者・開発者・運用担当）を同じ問いかけで聞く。聞いた読者は Step 2C でブリーフに書く（聞いたままにしない）。

### 2B-2. 置き場所と形式

- 文書の置き場所（推奨: `docs/`）と形式（Markdown / HTML サイト）を聞く
- HTML サイトなら、見た目の方向性（`show.mjs visuals`）の 1〜3 を選んでもらう

### 2B-3. `など` の扱い

曖昧語リストは初期値で `など` を止めない。手順書中心で `など` も禁止したいかを聞く（推奨: 止めない）。

## Step 2C: 文書群と読者を決める（既存・新規の両方）

**一度決めた読者・範囲は、文書群ごとのブリーフに残す。** 残さないと、文書を書くたびに読者を聞き直すことになる。

1. 検査する置き場所（2A-1 / 2B-2）を、**読者が同じものごとに文書群にまとめる**。読者が違う場所（利用者向けの使い方と、開発者向けのリファレンス）は別の文書群にする。
   どの文書群にも入らない文書（`README.md`）は、名前 `default` の文書群にまとめる
2. 文書群ごとに次の案を作り、**まとめて1回で**確かめてもらう（4問を超えるなら、文書群ごとに1問にまとめる。**案の表は問いの本文か直前の出力に書き**、承認か修正をもらう）。
   用語集に足す語の案（2A-4）があれば、同じ回に並べる

   | 項目 | 案の作り方 |
   |---|---|
   | 名前 | 英数字とハイフン（ファイル名 `doc-brief-<名前>.md` になる）。例: `usage`・`reference`・`default` |
   | 文書群の名前 | 日本語。例: 利用者向けの使い方 |
   | `paths` | その置き場所の glob（`docs/web/usage/**`）。`default` は README のように個別のファイルを列挙する。**`**` だけにしない**（コードに触れたときにも読み込まれる）。**`{a,b}` の形は使わない**（パターンを分けて並べる） |
   | 読者 | 読者プロファイル（beginner / engineer / operator / developer）と、そのプロジェクト固有の読者像（「初めて使うシニア。設定は家族が手伝う」）。既存なら文書の書きぶりから推測して示す。**技術者向けの製品を初めて使う人は engineer**（beginner は機械が苦手な人も含む読者、operator は障害時の運用担当で、どちらも観点がずれる） |
   | 扱わないこと | この文書群の責任の外にあること（「端末 OS の設定」）。無ければ「なし」 |
   | 事実の承認者 | 製品の振る舞いの正誤を判断する人（既定は依頼者） |
   | 読者向けの改訂履歴 | 読者に「いつ・どこを・どう変えたか」を見せるか。**案は「あり」で作る**（`default` の README も同じ）。アプリ内のヘルプのように見せる意味が無いと思うときも、「なし」は案の理由を添えて示し、依頼者に選んでもらう。**「あり」なら置き場所も決める**: 各文書の末尾の「改訂履歴」の節（既定）か、サイトの改訂履歴のページにまとめるか。まとめるなら `"set":{"読者向けの改訂履歴":{"読者向けの改訂履歴":"あり","置き場所":"web/manual/history.html"}}` のようにページのパスを**プロジェクトのルートから**書く（文書ごとの決め事の見出しと違い、`paths` の基点からではない）（完了処理の検査が、各文書ではなくそのページを見る） |

3. **依頼者が確かめた値は「確定」、推測のまま置いた値は「仮定」**で書く（Step 3）。仮定の値は、文書を書くときに `manual-writer` が確かめ直す

## 導入済みのプロジェクトに足す

0.6.0 以前に導入したプロジェクトにはブリーフが、0.7.0 以前なら内部の改訂記録が無く、`CLAUDE.md` の節も古い。**導入はやり直さず、足りないものだけを足す。**

1. `.claude/doc-harness.config.json` の `include` と、その場所の文書を2〜3本読み、Step 2C の案を作る
2. `CLAUDE.md` の「文書ルール（harness-doc）」の節と、最新版の節（`node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" claude-section`）を比べる。
   違えば、違う規則を1行ずつ挙げる（例:「規則1: 入口が manual-writer から plan-doc に変わった」「規則9: 改訂の記録が無い」）
   `docs-style/README.md`（利用者向けの使い方）も、最新版（`node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" style-readme`）と比べる。違えば、違う行を挙げる（例:「行単位の抑止を使ってよい場合が増えた」）
3. Step 2C の 2・3 と、上の節と `docs-style/README.md` の置き換え（「最新版で置き換える（推奨）／置き換えない」）を、**まとめて1回で**確かめる。
   `docs-style/README.md` は、プロジェクトが書き足した行があれば、置き換えた後の末尾に残す
4. Step 3 の 3（ブリーフを書く）と 4（内部の改訂記録を作る）を行う。置き換えると決めたら、`CLAUDE.md` の節（見出し「## 文書ルール（harness-doc）」から次の `## ` の前まで）を最新版で置き換える（`Edit`）。
   **プロジェクトが節に足した独自の規則があれば、置き換えた後の節の末尾に残す**（消さない）

## Step 3: 適用する

確認なしで適用してよい（このスキルが呼ばれたことが導入の依頼）。
**ただし `manual-writer` から別の作業の途中で来た場合は**、Step 1 の結果を1〜2行で示し、了承を得てから進める。

1. 雛形を置く

   ```bash
   node "${CLAUDE_SKILL_DIR}/scripts/apply.mjs" --dest "<導入先>"
   ```

   既存ファイルは上書きしない。変更が入る既存ファイルは `CLAUDE.md`（末尾に節を足す）だけ

2. 設定を書き込む。**`.claude/` 配下は `Edit` で書かず、このスクリプトで書く**（Claude Code が `.claude/` への書き込みに
   確認を求めるため。利用者に余計な確認を出さない）

   ```bash
   node "${CLAUDE_SKILL_DIR}/scripts/apply.mjs" --dest "<導入先>" --config '{"include":["docs/usage/**/*.md","README.md"],"glossaryFiles":[],"voice":{"endings":"keitai"}}'
   ```

   値は `include`（2A-1 / 2B-2）、`glossaryFiles`（2A-4）、`voice.endings`（`keitai` / `jotai` / `null`）。
   配列は置き換わり、`voice` は項目ごとに合成される。知らないキーを渡すとエラーで止まる

3. ブリーフを書く（Step 2C で決めた文書群ごとに1回）。`.claude/` 配下なので `Edit` で書かず、このスクリプトで書く

   ```bash
   node "${CLAUDE_SKILL_DIR}/scripts/apply.mjs" --dest "<導入先>" --brief '{"name":"usage","title":"利用者向けの使い方","paths":["docs/web/usage/**"],"by":"依頼者","set":{"読者":{"プロファイル":"beginner","読者像":"初めて使うシニア。設定は家族が手伝う"},"事実の承認者":{"承認者":"依頼者"},"読者向けの改訂履歴":{"読者向けの改訂履歴":"あり"}},"outOfScope":["端末 OS の設定"]}'
   ```

   推測のまま置く値は `{"value":"...","status":"仮定"}` の形で渡す。文書群の文体が `voice.md` と違うなら `"styleDiff":"..."` も渡す。
   書いたら `node "${CLAUDE_SKILL_DIR}/../../scripts/brief.mjs" list` で確かめる

4. 文書群ごとに、内部の改訂記録を雛形から作る（**必須**。改訂のたびに、改訂箇所・改訂内容・改訂意図を残す場所）

   ```bash
   node "${CLAUDE_SKILL_DIR}/../../scripts/history.mjs" init <文書群の名前> --dest "<導入先>"
   ```

5. 文書側を書き込む（`Edit`）

   | ファイル | 書くこと |
   |---|---|
   | `docs-style/voice.md` | 文体の表・見本の文・避けること・見た目・由来。`<!-- status: 未設定 -->` を `<!-- status: 設定済み -->` に替える |
   | `docs-style/glossary.md` | 2A-4 で確かめた表記の好み |
   | `docs-style/banned-words.txt` | 2B-3 で `など` を止めると決めたときだけ、`# など` の `#` を外す |

## Step 4: 動くことを確かめる

1. 置いたファイルを `ls` で確かめる
2. 検査対象の既存の文書を2本選び、検査を通してみる（**直さない。結果を見るだけ**）

   ```bash
   node "${CLAUDE_SKILL_DIR}/../../hooks/scripts/check-docs.mjs" <検査対象の文書のパス> <もう1本>
   ```

3. 既存の文書で指摘が多い場合は、その内訳を示す。**規則が合っていない**（踏襲すべき表記を止めている）なら、
   その場で用語集・曖昧語リストを直すかを聞く。**文書の側を勝手に直さない**

フックは再起動なしで有効になる（設定ファイルは書き込みのたびに読み直される）。
セッションを別のリポジトリで開いたまま導入したときも、フックは文書のパスから導入先の config を探すので効く。

## Step 5: 導入をコミットする（依頼者がコミットを許したときだけ）

置いたファイルだけを、パスを指定してコミットする（`CLAUDE.md`・`.claude/doc-harness.config.json`・`.claude/rules/doc-brief-*.md`・`docs-style/`）。
導入のファイルは検査対象の文書ではないので、コミット時の検査（改訂の記録）には止められない。
**コミットの文言に `doc-record: skip（…）` を書かない**（依頼者の承認を求める印で、導入には要らない。実地検証で、要らないのに書いた）。
`include` に既存の文書（例: `README.md`）が入っていて、導入と同時にその文書を直したときだけ、その文書の改訂の記録が要る。

## dev-harness 併用時（`devHarness: true`）

`docs/設計書/`・`docs/features/`・`docs/reviews/`・`docs/handoff/` は**自動で検査対象から外れる**（`apply.mjs` が設定する）。
これらは harness-core のスキルが書く開発者向けの記録で、検査すると `update-docs` のたびに止まる。

用語表は、harness-core の `glossary-keeper` が `.claude/rules/` に作るものがあれば、2A-4 で `glossaryFiles` に入れて
**1つにまとめる**（`docs-style/glossary.md` は空のまま）。
