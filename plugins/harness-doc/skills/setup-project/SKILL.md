# setup-project

今のプロジェクトに文書ハーネスを**対話で**導入する。**利用者にコマンドを打たせない。**
決めることは利用者に聞き、それ以外（ファイルを置く・設定を書く）はすべてこのスキルの中で行う。

> **なぜ対話にするか。** 文書の置き場所・文体・見た目はプロジェクトごとに違い、ハーネスの既定値を
> 押し付けると既存の文書と食い違う（実例: 用語集の初期値 `サーバー` が、`サーバ` で統一していた
> プロジェクトの51か所を止めた）。**既存のものは踏襲し、決まっていないものだけ選んでもらう。**

使うスクリプトと資料（`${CLAUDE_SKILL_DIR}` は絶対パスに置き換えて書く。シェル変数ではない）:

| 名前 | パス | 役割 |
|---|---|---|
| 棚卸し | `${CLAUDE_SKILL_DIR}/scripts/inventory.mjs` | 文書の置き場所・用語表・CSS を調べる（読むだけ） |
| 適用 | `${CLAUDE_SKILL_DIR}/scripts/apply.mjs` | 雛形を置く（既存ファイルは上書きしない） |
| 文体の見本集 | `node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" voices` | 新規のとき見せる |
| 見た目の方向性 | `node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" visuals` | 新規の HTML サイトのとき見せる |

資料は `Read` で開かず、`node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" voices`（または `visuals`）で出力して読む。
プラグインはプロジェクトの外に置かれ、`Read` だと権限の確認が出たり拒否されたりするため。

## 質問のしかた

- **`AskUserQuestion` ツールで選択肢として聞く。** 使えない環境では、番号付きの選択肢を文章で示して答えを待つ
- **1回の問いかけで聞くのは4問まで。** 関連する問いはまとめる
- **推奨の選択肢を先頭に置き、「（推奨）」と付ける。** 推奨の根拠（既存の文書から読み取った事実）を説明に書く
- 文体は**見本の文**を見せて選んでもらう。項目名だけでは選べない
- **既に決まっていること（既存の文書から明らかなこと）は聞かない。** 読み取った結果として示し、違っていれば直してもらう

## Step 1: 棚卸しする

```bash
node "${CLAUDE_SKILL_DIR}/scripts/inventory.mjs" --dest "<導入先>"
```

導入先は $ARGUMENTS のパス、無ければ今のプロジェクトのルート。

| 結果 | 次 |
|---|---|
| `hasHarnessDoc: true` | 導入済み。**導入をやり直さない。** 文体を変えたいなら `change-tone` を案内して終える |
| `existing: true`（利用者向けの文書の候補がある） | Step 2A（既存） |
| `existing: false` | Step 2B（新規） |

判定に迷う場合（候補が README だけ）は、「既存の文書を踏襲しますか、新しく決めますか」と1問聞く。

## Step 2A: 既存 — 読み取って踏襲する

### 2A-1. 検査する文書の置き場所を決める

`candidates`（利用者向けの文書の候補）を**複数選択**で聞く。`docDirs` の数を説明に添える。

- 候補にはアプリの画面（`web-ui/public` のような）や開発文書も混ざりうる。**決めつけずに選んでもらう**
- `managedByDevHarness: true` の場所（dev-harness の設計書・機能設計書・レビュー記録・引き継ぎ）は候補に出さない（自動で対象外）
- 選ばれた場所から `include` を作る（`<場所>/**/*.md`・`<場所>/**/*.html`。その場所にある拡張子だけ）。`README.md` は既定で入れる

### 2A-2. 今の文体を読み取る

選ばれた場所から、**文書の種類ごとに2〜3本**を読む（全部は読まない）。次を数えて読み取る。

| 項目 | 読み取り方 |
|---|---|
| 文末 | 句点で終わる文の、敬体（です・ます）と常体（だ・である）の割合 |
| 語りかけの温度 | 「〜してください」「〜しましょう」の有無、感嘆符、やわらかい言い回し |
| 専門用語 | 説明なしで使っている専門語の多さ |
| 一文の長さ | 句点までの字数のおおよその中央値 |
| 表記の好み | 長音（`サーバ` / `サーバー`）・送り仮名・数字（全角/半角）・括弧。**多数派を正とする** |
| 見本の文 | 実物から、その文書らしさがよく出ている文を2〜3文引用する |

**場所ごとに文体が違う**ことがある（例: 利用者向けは敬体、リファレンスは常体）。違っていれば場所ごとに書き分け、
`voice.endings` は `null`（機械では検査しない）にする。

### 2A-3. 読み取った結果を確かめてもらう

読み取った文体を表と見本の文で示し、1問で聞く。

- 「このまま踏襲する（推奨）」/「一部を変える」/「見本集から選び直す」
- 「一部を変える」なら、変えたい項目を続けて聞く
- 「選び直す」なら Step 2B-1 の質問をする

### 2A-4. 用語表と見た目

- `termFiles` があれば、「この用語表を検査にも使いますか（推奨: はい）」と聞く。はいなら `glossaryFiles` に入れる。
  **このとき `docs-style/glossary.md` は空のまま置き、二重に管理しない**
- 表記の好み（長音・送り仮名・数字）で多数派がはっきりしたものは、`docs-style/glossary.md` に足す案を示して確かめる
- HTML の場所を選んだ場合、`cssFiles` から**その場所が読み込んでいる CSS**（HTML の `<link>` を見る）を特定し、
  `voice.md` の「従う CSS」に書く。**既存の見た目は変えないので、聞かない**
- 図の描き方（スクリーンショット・CSS のモック・CSS の図部品）は実物から読み取って書く

## Step 2B: 新規 — 見本から選んでもらう

### 2B-1. 文体を選ぶ

文体の見本集（`show.mjs voices`）の A〜D を、**各見本の文を説明に入れて**選択肢として出す。読者の想定を先に聞いた方が選びやすければ、
「主な読者」（初めての人・一般の利用者・開発者・運用担当）を同じ問いかけで聞く。

### 2B-2. 置き場所と形式

- 文書の置き場所（推奨: `docs/`）と形式（Markdown / HTML サイト）を聞く
- HTML サイトなら、見た目の方向性（`show.mjs visuals`）の 1〜3 を選んでもらう

### 2B-3. `など` の扱い

曖昧語リストは初期値で `など` を止めない。手順書中心で `など` も禁止したいかを聞く（推奨: 止めない）。

## Step 3: 適用する

確認なしで適用してよい（このスキルが呼ばれたことが導入の依頼）。
**ただし `manual-writer` から別の作業の途中で来た場合は**、Step 1 の結果を1〜2行で示し、了承を得てから進める。

1. 雛形を置く

   ```bash
   node "${CLAUDE_SKILL_DIR}/scripts/apply.mjs" --dest "<導入先>"
   ```

   既存ファイルは上書きしない。変更が入る既存ファイルは `CLAUDE.md`（末尾に節を足す）だけ

2. 設定を書き込む。**`.claude/` 配下は `Edit` で書かず、このスクリプトで書く**（Claude Code が `.claude/` への書き込みに
   確認を求めるため。利用者に余計な確認を出さない）

   ```bash
   node "${CLAUDE_SKILL_DIR}/scripts/apply.mjs" --dest "<導入先>" --config '{"include":["docs/usage/**/*.md","README.md"],"glossaryFiles":[],"voice":{"endings":"keitai"}}'
   ```

   値は `include`（2A-1 / 2B-2）、`glossaryFiles`（2A-4）、`voice.endings`（`keitai` / `jotai` / `null`）。
   配列は置き換わり、`voice` は項目ごとに合成される。知らないキーを渡すとエラーで止まる

3. 文書側を書き込む（`Edit`）

   | ファイル | 書くこと |
   |---|---|
   | `docs-style/voice.md` | 文体の表・見本の文・避けること・見た目・由来。`<!-- status: 未設定 -->` を `<!-- status: 設定済み -->` に替える |
   | `docs-style/glossary.md` | 2A-4 で確かめた表記の好み |
   | `docs-style/banned-words.txt` | 2B-3 で `など` を止めると決めたときだけ、`# など` の `#` を外す |

## Step 4: 動くことを確かめる

1. 置いたファイルを `ls` で確かめる
2. 検査対象の既存の文書を2本選び、検査を通してみる（**直さない。結果を見るだけ**）

   ```bash
   node "${CLAUDE_SKILL_DIR}/../../hooks/scripts/check-docs.mjs" <検査対象の文書のパス> <もう1本>
   ```

3. 既存の文書で指摘が多い場合は、その内訳を示す。**規則が合っていない**（踏襲すべき表記を止めている）なら、
   その場で用語集・曖昧語リストを直すかを聞く。**文書の側を勝手に直さない**

フックは再起動なしで有効になる（設定ファイルは書き込みのたびに読み直される）。

## dev-harness 併用時（`devHarness: true`）

`docs/設計書/`・`docs/features/`・`docs/reviews/`・`docs/handoff/` は**自動で検査対象から外れる**（`apply.mjs` が設定する）。
これらは harness-core のスキルが書く開発者向けの記録で、検査すると `update-docs` のたびに止まる。

用語表は、harness-core の `glossary-keeper` が `.claude/rules/` に作るものがあれば、2A-4 で `glossaryFiles` に入れて
**1つにまとめる**（`docs-style/glossary.md` は空のまま）。
