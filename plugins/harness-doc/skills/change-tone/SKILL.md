# change-tone

既存の文書の**テイストだけ**を変える。**書いてある事実・手順・構成は変えない。**

> **なぜ別のスキルか。** `manual-writer` は「読者に伝わるように書き直す」ので、構成も中身も変える。
> テイストの変更は逆で、中身を変えずに調子だけ揃えたい。混ぜると、調子を変えたつもりで手順が消える。

使う資料（`${CLAUDE_SKILL_DIR}` は絶対パスに置き換えて書く）:

| 名前 | パス |
|---|---|
| 文体の見本集 | `node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" voices` |
| 見た目の方向性 | `node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" visuals` |
| 検査 | `${CLAUDE_SKILL_DIR}/../../hooks/scripts/check-docs.mjs` |

資料は `Read` で開かず、`node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" voices`（または `visuals`）で出力して読む。
プラグインはプロジェクトの外に置かれ、`Read` だと権限の確認が出たり拒否されたりするため。

質問は `AskUserQuestion` ツールで選択肢として出す（使えない環境では番号付きの選択肢を文章で示す）。
推奨の選択肢を先頭に置き、「（推奨）」と付ける。

## Step 0: 導入済みかを確かめる

`.claude/doc-harness.config.json` と `docs-style/voice.md` があるかを見る。
無ければ「先に文書ハーネスを導入します」と伝え、了承を得て `/harness-doc:setup-project` を通してから戻る。

## Step 1: 何を、どう変えるかを決める

**文書を書く・直す依頼の入口は `/harness-doc:plan-doc`。** 利用者からこのスキルを直接頼まれたら、先に plan-doc の受付と規模判定を通す（規模と前提を1回で確かめ、ここに戻る）。
plan-doc から渡されたときは、承認済みの規模と前提を受け取っているので、同じことを聞き直さない。
見た目を変えるときの CSS の値の表（下の「見た目を変える場合」）は、Step 2 の見本と**同じ問い**で示す（問いを増やさない）。

1. **対象。** $ARGUMENTS にあればそれ。無ければ、検査対象（config の `include`）の場所を選択肢にして聞く（複数選択）
2. **何を変えるか。** 依頼文から分かれば聞かない。分からなければ聞く:
   - 文体（文末・温度・専門用語・一文の長さ）
   - 表記（長音・数字・用語の統一）
   - 見た目（HTML だけ。文字の大きさ・配色・余白）
3. **どう変えるか。** 依頼文が具体的（「です・ます調に」）なら、それを `voice.md` の項目に当てはめる。
   漠然としている（「もっとやさしく」）なら、文体の見本集（`show.mjs voices`）の見本から近いものを選んでもらう

## Step 2: 変えた後の見本を見せて確かめる（省略しない）

対象から**代表的な段落を1つ**選び、**今の文と、変えた後の文を並べて**示す。

```text
【今】  設定は config.json に保存する。保存後の再起動は不要である。
【変更後】設定は config.json というファイルに保存されます。保存したあと、再起動する必要はありません。
```

選択肢: 「この調子で全体を変える（推奨）」/「もう少し調整する」/「やめる」。
「調整する」なら、どこをどう変えるかを聞いて見本を作り直す。**合意するまで書き換えに進まない。**

あわせて、変更の規模を伝える（対象の本数・おおよその変更箇所数）。

## Step 3: voice.md（またはブリーフの「文体の差分」）を更新する

**どこに書くかは、対象の範囲で決まる。**

| 対象 | 書く先 |
|---|---|
| 検査対象の全体（プロジェクトのすべての文書群） | `docs-style/voice.md` |
| **一部の文書群だけ** | その文書群のブリーフの「文体の差分」（`voice.md` との違いだけを書く）。**`voice.md` は変えない**。変えると、触らなかった文書群の文書がその時点で決まり違反になる |

ブリーフの「文体の差分」は次で書く（`.claude/` 配下なので `Edit` で書かない）。どの文書群かは `node "${CLAUDE_SKILL_DIR}/../../scripts/brief.mjs" list` で確かめる。
**`styleDiff` は丸ごと置き換わる。** 先に `brief.mjs show <その文書群の文書のパス>` で今の「文体の差分」を読み、残すものと合わせた文を渡す。`note` に「change-tone。前は〜」と添えると由来に残る。

```bash
node "${CLAUDE_SKILL_DIR}/../setup-project/scripts/apply.mjs" --brief '{"name":"usage","by":"依頼者","styleDiff":"文末は敬体（です・ます）。語りかけはやわらかく、専門用語は使わない。見本: 「緑のボタンを押すと、電話がかかります。」"}'
```

一部の文書群だけ**文末**を変えて、文書群ごとに文末が違うことになったら、`voice.endings` を `null` にする（文末の機械の検査はプロジェクト全体に一律で効くため、止める）。完了報告にそう書く。

合意した文体を書くのは**書き換えの前**（書き換えの途中で中断しても、次に何に揃えるかが残る）。以下は `voice.md` に書く場合の手順。

- 文体の表・見本の文（Step 2 で合意した変更後の文）を書き換える
- 「由来」に「YYYY-MM-DD change-tone。〜を〜に変えた」を1行足す（前の由来は消さない）
- 文末を変えた場合は `voice.endings` も変える。`.claude/` 配下は `Edit` で書かず、次で書く

  ```bash
  node "${CLAUDE_SKILL_DIR}/../setup-project/scripts/apply.mjs" --config '{"voice":{"endings":"keitai"}}'
  ```

## Step 4: 書き換える

1. **作業前の状態を残す。** git 管理下なら `git status --short` で、対象に未コミットの変更が無いことを確かめる。
   あれば、先にコミットするかを聞く（混ざると差分で確かめられない）
2. 対象を**1本ずつ**書き換える。守ること:

   | 変えてよい | 変えない |
   |---|---|
   | 文末・語尾、言い回し、語りかけ、文の区切り（長い文を2つに分ける） | 書いてある事実・数値・手順の順番と数 |
   | 専門用語の言い換え（用語集にあるものは用語集に従う） | 画面名・ボタン名・コマンド・コード・ファイル名 |
   | 表記（長音・数字） | 見出しの構成、リンク先、画像 |
   | HTML: 本文のテキスト | HTML: タグの構造・クラス名・属性 |

3. 本数が多い場合（10本を超える）は、`Agent` で5本ずつのまとまりに分けて並列で書き換えてよい。
   その場合も、各エージェントに**合意した見本の文・voice.md のパス・上の表**を必ず渡す

### 見た目を変える場合（HTML だけ）

- **変えるのは CSS の値だけ**（色・文字の大きさ・行の高さ・余白・最大幅）。HTML の構造は変えない
- まず既存の CSS を読み、変える値（変数や該当のセレクター）と、変更前→変更後の値を**表で示して合意を得る**
- 見た目の方向性（`show.mjs visuals`）の「どの方向性でも守ること」（コントラスト比 4.5:1 以上ほか）を下回る変更は、理由を添えて止める
- `voice.md` の「見た目」も更新する

## Step 5: 確かめる

1. **中身が変わっていないか。** `git diff` で全変更を読む。事実・数値・手順・画面名・コードが変わっていたら戻す。
   **これがこのスキルで最も大事な確認**（文章の変更は、壊れても検査で検出されない）
2. 検査を通す

   ```bash
   node "${CLAUDE_SKILL_DIR}/../../hooks/scripts/check-docs.mjs" <書き換えた文書...>
   ```

3. 代表的な1本を `harness-doc:doc-reviewer` に渡し、**新しい voice.md に沿っているか**を点検してもらう。
   渡すもの: 文書の絶対パス、`docs-style/voice.md` の絶対パス、読者プロファイル

## Step 6: 改訂の記録を残す

**テイストの変更も改訂なので、記録を必ず残す。** 作業中に「この言い方はやめて」「覚えておいて」と言われたことがあれば、書き戻すかを**記録を書く前に**1問だけ聞き、答えを反映してから書く（記録は追記だけで、書いた節は後から直さない）。

1. 内部の改訂記録に1節を足す（必須）。書き換えた文書をまとめて1節にし、`docs` に全部を並べる（文書群ごとに1回。文書群をまたぐなら文書群ごとに分ける）

   ```bash
   node "${CLAUDE_SKILL_DIR}/../../scripts/history.mjs" add --json '{"docs":["docs/usage/a.md","docs/usage/b.md"],"label":"テイスト変更: a.md ほか1本","size":"M","改訂箇所":"全体の文末と語りかけ","改訂内容":"常体から敬体に。専門用語を言い換えた","改訂意図":"初めて使う読者に硬く感じられていた（依頼者の指摘）","読者向けの改訂履歴":"文章をやさしい言葉に書き直しました","変更者・承認者":"Claude・依頼者","改訂設計書":"なし（P2a の暫定）"}'
   ```

2. ブリーフで読者向けの改訂履歴が「あり」の文書には、それぞれの「改訂履歴」の節に1行足す（「文章をやさしい言葉に書き直しました」）
3. 完了処理の検査を通す（`node "${CLAUDE_SKILL_DIR}/../../scripts/complete-doc.mjs" <書き換えた文書...>`）。`NG` が出たら直す

## 完了報告

| 項目 | 内容 |
|---|---|
| 対象 | 本数と場所 |
| 改訂の記録 | 内部の改訂記録に足した節・読者向けの改訂履歴に書いた1行・完了処理の検査の結果 |
| 変えたこと | 変更前 → 変更後（文体の表の差分）。見本の文 |
| 変えなかったこと | 事実・構成・画面名・コードを変えていないことを `git diff` で確かめた旨 |
| 検査 | check-docs の結果。読者役レビューの指摘（あれば） |
| voice.md / ブリーフ | 更新した項目と、どちらに書いたか（一部の文書群だけなら「文体の差分」）。`voice.endings` を変えたか |

コミットは利用者に確かめてから行う（テイストの変更は差分が大きく、見てから判断したい人が多い）。

> 読者そのものを変えたい（「家族向けにしたい」）、扱う範囲を変えたいという依頼は、テイストの変更ではない。`/harness-doc:change-policy` を案内する。
