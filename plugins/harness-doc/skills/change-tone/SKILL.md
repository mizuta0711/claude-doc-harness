# change-tone

既存の文書の**テイストだけ**を変える。**書いてある事実・手順・構成は変えない。**

> **なぜ別のスキルか。** `manual-writer` は「読者に伝わるように書き直す」ので、構成も中身も変える。
> テイストの変更は逆で、中身を変えずに調子だけ揃えたい。混ぜると、調子を変えたつもりで手順が消える。

**入口は `/harness-doc:plan-doc`。** 何をどう変えるかと、変えた後の見本（試作）は、plan-doc のテイスト変更の経路（`show.mjs path tone`）で決めて承認を取る。
このスキルは、承認済みの改訂設計書（`docs-style/plans/*.md`）を受け取って書き換える。
**利用者からこのスキルを直接頼まれたら、先に `/harness-doc:plan-doc` の受付から始め直す**（改訂設計書と試作の承認が無いまま書き換えない）。

使う資料（`${CLAUDE_SKILL_DIR}` は絶対パスに置き換えて書く）:

| 名前 | コマンド |
|---|---|
| 完了処理の検査・前後の比べ | `node "${CLAUDE_SKILL_DIR}/../../scripts/complete-doc.mjs" <文書...>`・`compare <文書...>` |
| 完了前の確認と完了処理の手順 | `node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" path finish` |
| 検査 | `node "${CLAUDE_SKILL_DIR}/../../hooks/scripts/check-docs.mjs" --changed <文書...>`（直前のコミットより増えた指摘だけで判定する。前からある指摘は直さない） |

## Step 0: 受け取るものを確かめる

- 改訂設計書がある。表の「性質と規模」が「テイスト変更」で、「試作」の節に承認した見本があり、「承認」に日付がある
- 無ければ書き換えずに、plan-doc の受付から始め直す

## Step 1: 作業前の基準点を記録する

```bash
node "${CLAUDE_SKILL_DIR}/../../scripts/complete-doc.mjs" --mark <書き換える文書...>
```

plan-doc で記録済みでも、もう一度 `--mark` してよい（同じコミットの上で、まだ記録を書いていなければ上書きせずに足す）。

文末を変えるときは、plan-doc が書き換えの前に文末の検査（`voice.endings`）を止めているはず（`show.mjs path tone` の 4-2）。止めていなければ、ここで止める（改訂方針に今の値を書いてから `apply.mjs --config '{"voice":{"endings":null}}'`）。止めないと、書き換えのたびに `check-docs` が新しい文末を止める。

**改訂設計書のタスク一覧と受け入れ基準は、終えるたびにチェックする**（完了処理の検査が未チェックを止める）。

## Step 2: 書き換える

対象を**1本ずつ**、**`Edit` で**書き換える（Bash の python や sed で一括置換しない。検査のフックが働かず、改行コードも崩れやすい）。
**見本は改訂設計書の「試作」の節。** 全体をそれに揃える。守ること:

| 変えてよい | 変えない |
|---|---|
| 文末・語尾、言い回し、語りかけ、文の区切り（長い文を2つに分ける） | 書いてある事実・数値・手順の順番と数 |
| 専門用語の言い換え（用語集にあるものは用語集に従う） | 画面名・ボタン名・コマンド・コード・ファイル名 |
| 表記（長音・数字） | 見出しの構成、リンク先、画像 |
| HTML: 本文のテキスト・CSS の値 | HTML: タグの構造・クラス名・属性 |

- 本数が多い場合（10本を超える）は、`Agent` で5本ずつのまとまりに分けて並列で書き換えてよい。各エージェントに**改訂設計書のパスと上の表**を必ず渡す（見本は設計書の「試作」の節にある）
- 見た目を変えるときは、承認した CSS の値の表どおりに CSS の値だけを変える。HTML の構造は変えない
- 書き換えの途中で、前提や用語の説明を足さないと読者に届かないと分かったら、書き換えを止める（テイスト変更の範囲を超えるため）。完了前の確認で「改訂として L で直すか」を聞く（finish の表にある）。直すなら、書き換えた分を `complete-doc.mjs restore` で戻し、plan-doc の L の経路で改訂設計書を作り直す

終えたら、改訂設計書のタスク一覧の「書き換える」にチェックを付ける。

## Step 3: 確かめる

1. **中身が変わっていないか。** `git diff` で全変更を読む。事実・数値・手順・画面名・コードが変わっていたら戻す。
   **これがこのスキルで最も大事な確認**（文章の変更は、壊れても検査で検出されない）。受け入れ基準の1つ目にチェックを付ける
2. 検査を通す（`check-docs.mjs --changed <書き換えた文書...>`。前からある指摘は直さない。テイスト変更の範囲の外）
3. `harness-doc:doc-reviewer` に、**承認した見本の調子に沿っているか**を点検してもらう（見本と比べる点検）。
   **点検する本数**: 1人で書き換えたなら代表の1本。並列のエージェントに分けて書き換えたなら、**まとまりごとに1本ずつ**（まとまりごとのずれは、代表の1本では見つからない）。
   渡すもの: 文書の絶対パス、試作の見本の文（改訂設計書の「試作」の節から**全文で貼る**。読者役は改訂設計書を読めない）、読者プロファイル。
   **`voice.md` は渡さない**（変更前の決まりなので、見本と食い違う。渡すと新しい文を「決まりとずれている」と指摘される）。
   「見本と比べて、調子が揃っていない箇所を挙げる」と頼む。受け入れ基準の2つ目は、この結果で判定する。
   **結果が返ったら、直す前に、指摘を全件、改訂設計書の「読者役の指摘」の表に写す**（指摘が0件なら「指摘なし」の1行。空のままだと完了処理の検査が止める）
4. 一部の文書群だけ変えたときは、ほかの文書群の文書が `git diff` に出ていないことを確かめる（受け入れ基準の3つ目）

## Step 4: 完了前の確認と完了処理

**手順は plan-doc の経路のファイルにある。** 次で出力して読み、それに従う。テイスト変更では、完了前の確認で採用が決まってから `voice.md`（かブリーフの「文体の差分」）を書く（finish の 3-1）。

```bash
node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" path finish
```

内部の改訂記録の節は、書き換えた文書をまとめて1節にし、`docs` に全部を並べる（文書群ごとに1回）。`label` は「テイスト変更: <最初の文書> ほか N 本」にする。

## 完了報告

| 項目 | 内容 |
|---|---|
| 対象 | 本数と場所 |
| 性質と規模 | 承認したもの |
| 改訂の記録 | 内部の改訂記録に足した節・読者向けの改訂履歴に書いた1行・完了処理の検査の結果 |
| 変えたこと | 変更前 → 変更後（文体の表の差分）。見本の文 |
| 変えなかったこと | 事実・構成・画面名・コードを変えていないことを `git diff` で確かめた旨 |
| 検査 | check-docs の結果。読者役が見本と比べた結果 |
| voice.md / ブリーフ | 更新した項目と、どちらに書いたか（一部の文書群だけなら「文体の差分」）、または「変えなかった（このページだけの調子。決まりの範囲に収まる）」。`voice.endings` を変えたか |
| 依頼者が次にやること | **この作業の変更だけでコミットする**（テイストの変更は差分が大きいので、見てからコミットしたい人が多い） |

> 読者そのものを変えたい（「家族向けにしたい」）、扱う範囲を変えたいという依頼は、テイストの変更ではない。plan-doc が方針変更と判定し、`change-policy` に渡す。
