# plan-doc の経路: 完了前の確認と完了処理（M・L・テイスト変更）

`manual-writer`（新規作成・改訂・誤りの修正）と `change-tone`（テイスト変更）が、最後の Step でこれを読む。改訂設計書（`docs-style/plans/*.md`）がある作業の終わり方。
下の `<プラグイン>` は、呼んだスキルから見て `${CLAUDE_SKILL_DIR}/../..`（絶対パスに置き換えて書く）。

## 1. 前後確認を作る（既存の文書を変えたとき）

```bash
node "<プラグイン>/scripts/complete-doc.mjs" compare --limit <改訂設計書の分量の上限の倍率> <変えた文書のパス...>
```

改訂設計書の「前後確認」の節に、次を書く。**空のままだと完了処理の検査が止める。**

| 書くもの | 作り方 |
|---|---|
| 数値と見出しの比較 | `compare` の出力をそのまま貼る |
| **事実の変更の一覧** | 箇所・前・後・変えた意図・根拠（ファイルと行）。機械では作れないので、書き手が書く。無ければ「事実の変更なし」 |

**要約の質が、この確認の成否を決める。** 差分を全部見せず、判断に要るものだけを1画面に収める。

新規作成なら、タスク一覧の「前後確認を書く」の行の末尾に「対象外（新規作成）」と書き足す。

## 2. 完了前の確認（依頼者に1回）

ためておいた問いを、**1回にまとめて**聞く。中身は問いの直前の出力に全部書く（設計書のパスだけを示さない）。
**問いを出す前に、問いの出し方を読む**（推奨を付けない問い・4問への収め方。会話が圧縮されていても、ここで読み直す）:

```bash
node "<プラグイン>/presets/show.mjs" path questions
```

| 中身 | いつ入るか |
|---|---|
| 前後確認（上の 1） | 既存の文書を変えたとき |
| **未回答の問い合わせ** | 改訂設計書の「問い合わせ」に回答の無い行があれば。一覧を出し、問いの出し方の 2 の4番の形で聞く（事実の確認で「分からない」を選ばれたものは聞き直さない） |
| **食い違い（製品の判断）** | 改訂設計書の「食い違い」に行があれば。**依頼者の選択が空の行が残っていると、完了処理の検査が止める。** 一覧に「今の動きとして書くなら案の文」を添え、推奨を付けずに聞く。選ばれなかったものは本文に書かない（印を残す） |
| **安全に関わる記述** | 安全・個人情報に関わる文書の外の問題を見つけたとき。それに触れる本文の記述（「〜しないと誰もつなげません」）を並べ、外すかを聞く |
| **回答の聞き直し** | 依頼者の回答と食い違う事実が作業中に見つかったとき（回答した入手先のページが無い） |
| **分量の上限を超えた文書** | `compare --limit` が ⚠️ を出したとき。文書ごとの倍率と、増えた理由 |
| **最後の読者役の後に直した箇所** | 最後の読者役の後に本文を直した・事実を足したとき（改訂設計書の「読者役の指摘」に書いた箇所）。「直した分だけもう1回読者役にかける」を採用の問いの選択肢に足す |
| 読者役が2回で受け入れ基準を満たさなかったときの判断（基準を直す・範囲外とする・もう1回まわす） | あれば |
| 改訂の範囲の外の致命的・受け入れ基準を満たせない原因（範囲を広げて直す・次の改訂に回す） | 読者役が「（改訂範囲外）」を付けて致命的のまま返したとき（manual-writer の Step 6） |
| 意図を理由に2回見送った指摘（意図を保つか・変えるか） | あれば |
| 書き戻し・用語の追加 | あれば |
| **テイスト変更: `voice.md`（かブリーフの「文体の差分」）に書く中身** | テイスト変更のとき。改訂方針の「書く先」と、書く文（文体の表の差分・見本の文）を示す。採用なら 3-1 で書く。**対象が文書群の一部（1本・数本）なら、推奨は「決まりは変えない」**（経路の tone の 4-1） |
| 試作の見本を、次の文書にも効くよう `voice.md` の見本に残すか | 試作をした L・テイスト変更のとき（要素ごとの見本は、次の文書の書き手が揃える基準になる） |
| L で文体を `voice.md` から変えたなら、`voice.md`（かブリーフの「文体の差分」）に書くか | 試作で文体を変えた L のとき。書くなら 3-1 と同じ手順。対象が文書群の一部なら、推奨は「決まりは変えない」 |
| テイスト変更の途中で、前提や用語の説明が要ると分かった箇所を、改訂として L で直すか | `change-tone` が書き換えを止めたとき。直すなら書き換えた分を `restore` で戻し、plan-doc の L の経路で改訂設計書を作り直す（このテイスト変更は「中止」にする） |

全体の選択肢は「このまま採用（推奨）」「一部を戻す（どこを）」「やり直す」。
**試作のファイル（名前に `.proto-` が入ったもの）が残っていたら、この前に消す**（残っていると完了処理の検査が止める）。

- **一部を戻す**: 指定された箇所を `Edit` で戻し、前後確認を書き直す（問いは増やさない）
- **やり直す**: 作業前に戻すかを確かめる。戻す文書ごとに `compare` の結果を示し、**作業中に依頼者が手で直した分も消える**ことを同じ問いで伝える。承認されたら戻し、改訂設計書の状態を「中止」にして `completed/` に移す。記録は書かない（文書は変わっていない）。文末の検査（`voice.endings`）を止めていたら、改訂方針に書いた元の値に戻す

  ```bash
  node "<プラグイン>/scripts/complete-doc.mjs" restore <文書のパス...>
  node "<プラグイン>/scripts/complete-doc.mjs" --clear
  ```

  この確かめは安全のための止め所なので、確認の回数に数えない

答えを本文・ブリーフ・用語集に反映し、改訂設計書の該当するタスクと受け入れ基準にチェックを付ける。満たさないと決めたものは、行を消さずに末尾に「対象外（理由）」と書く。

## 3. 完了処理

1. 改訂設計書の状態を「完了」にし、`docs-style/plans/completed/` に移す（`Write` で新しい場所に書き、元を消す。git で追跡しているなら `git mv`）
2. **内部の改訂記録に1節を足す**（必須）。`size` は承認した規模、`改訂設計書` は移した後のパス。ついでに直した文書（目次・リンク元）があるなら `docs` に全部並べる。読者向けの改訂履歴をまとめのページ（ブリーフの「置き場所」）に書いたなら、そのページも `docs` に入れる（ページも変わった文書なので、記録が要る）

   ```bash
   node "<プラグイン>/scripts/history.mjs" add --json '{"docs":["docs/usage/phone.md"],"size":"M","改訂箇所":"手順1〜4・うまくいかない場合","改訂内容":"権限の説明を手順の前に移し、通話の切り方を足した","改訂意図":"初めて使う読者が、発信の前に許可の画面で止まらないように","根拠":"MainActivity.kt:168-181","見送ったこと・決めたこと":"機内モードの解除は扱わない（ブリーフの扱わないこと。読者役の指摘を見送り）","読者向けの改訂履歴":"手順1：電話の許可の説明を手順の前に移しました","変更者・承認者":"Claude・依頼者","改訂設計書":"docs-style/plans/completed/20261005_phone.md"}'
   ```

3. ブリーフで読者向けの改訂履歴が「あり」なら、文書の「改訂履歴」の節に1行（ブリーフの「置き場所」がまとめのページのパス（例: `web/manual/history.html`）なら、そのページに1行で、各文書には書かない。新規作成なら「初版」。テイスト変更なら、書き換えた文書それぞれに「文章をやさしい言葉に書き直しました」のような1行）
4. テイスト変更と、文体を変えた L では、下の 3-1 で `voice.md`（かブリーフの「文体の差分」）を書く
5. 完了処理の検査と完了報告（下の 3-2）

### 3-1. voice.md（かブリーフの「文体の差分」）を書く（テイスト変更・文体を変えた L）

**完了前の確認で採用が決まってから書く**（試作の承認の時点で書くと、「やり直す」になったときに決まりだけが変わったまま残る）。書く先は改訂設計書の改訂方針にある。

- `docs-style/voice.md` に書くとき: 文体の表・見本の文（承認した試作の文）を書き換え、「由来」に「YYYY-MM-DD テイスト変更。〜を〜に変えた（改訂設計書のパス）」を1行足す（前の由来は消さない）。見た目を変えたなら「見た目」も書く
- ブリーフの「文体の差分」に書くとき: `.claude/` 配下なので `Edit` で書かず、スクリプトで書く。**`styleDiff` は丸ごと置き換わる**ので、先に `brief.mjs show <その文書群の文書のパス>` で今の「文体の差分」を読み、残すものと合わせた文を渡す

  ```bash
  node "<プラグイン>/skills/setup-project/scripts/apply.mjs" --brief '{"name":"usage","by":"依頼者","styleDiff":"文末は敬体（です・ます）。語りかけはやわらかく、専門用語は使わない。見本: 「緑のボタンを押すと、電話がかかります。」"}'
  ```

- 文末を変えたら `voice.endings` を新しい値にする（`apply.mjs --config '{"voice":{"endings":"keitai"}}'`。書き換えの前に `null` にしてあるはず。経路の tone の 4-2）。**一部の文書群だけ文末を変えて文書群ごとに文末が違うことになったら、`null` のままにする**（文末の機械の検査はプロジェクト全体に一律で効くため）。「やり直す」なら、改訂方針に書いた元の値に戻す
- 完了前の確認で「見本を voice.md に残す」と決まったら、`voice.md` の「要素ごとの見本の文」に足す

### 3-2. 完了処理の検査と完了報告

1. **完了処理の検査を通す。** 書いた・直した文書をすべて渡す

   ```bash
   node "<プラグイン>/scripts/complete-doc.mjs" <書いた・直した文書のパス...>
   ```

   `NG` が出たら直す（改訂設計書の未チェック・前後確認の空・読者役の指摘の空・食い違いの選択の空・記録の欠け・試作のファイルの残り・回答済みや表に無い番号の問い合わせの印）。**未回答の問い合わせの印は NG にならない**（改訂設計書の問い合わせ表で回答が空の番号。警告に出るので、完了報告の「問い合わせ」に全部載せる）。「判定できない」（基準点が無い）は直そうとせず、完了報告にそう書く
2. 完了報告を出す（呼んだスキルの「完了報告」の表。**表の形で出す**。行を省かない）。表の行に次を足す。
   - **読者役を通っていない箇所**: 完了前の確認の後に初めて書いた本文（今の動きとして書くと選ばれた食い違い・回答で埋めた箇所）と、最後の読者役の後に直した箇所。無ければ「なし」
   - **確認のために作ったもの・変えた設定**: 画像・エミュレーター・端末の言語や `adb root`・一時のファイル。消したか、残したか。無ければ「なし」
   ここでは新しく問わない。**コミットに入れるファイルを並べて添える**: 書いた・直した文書、内部の改訂記録（`docs-style/history/<文書群>.md`）、`completed/` に移した改訂設計書と、移す前のパス（消したことをコミットに入れる）。改訂設計書を入れ忘れると、コミット時の検査が止める。**この作業の変更だけでコミットする**（前の作業とまとめると、コミット時の検査が作業ごとの記録を見分けられない）
