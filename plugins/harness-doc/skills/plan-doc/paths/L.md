# plan-doc の経路: L（新規作成・改訂）

規模 L（新しい文書群・読者の変更・2本以上にまたがる・範囲が決まっていない「分かりにくいので直して」）と承認されたら、この手順で進める。
`${CLAUDE_SKILL_DIR}` は plan-doc のフォルダー（絶対パスに置き換えて書く）。

**確認の回数は L で4回**（規模と前提 → Stage 1 → 試作 → 完了前の確認）。

> **なぜ M より2段多いか。** 文書群の全体や読者を変える改訂は、本文を書いた後で直すと手戻りが大きい。
> 目次の段階で読者役に点検させ（安い）、文章の調子は試作で合意してから全体を書く。「やさしく」の解釈は人ごとに違い、文章の設計書では合意できない。

## 1. 改訂設計書を作る

M の経路（`show.mjs path M`）の「1. 改訂設計書を作る」と同じ。ただし次の点が違う。**M の「2. 承認を取る」は行わない**（Stage 1 の承認が兼ねる。行うと確認が5回になる）。

- 表の「性質と規模」は「改訂・L」か「新規作成・L」。「承認」には、Stage 1 と試作の承認の日付を書く
- 新規作成なら、表の「入口への登録」の行に、どの入口のファイルの、どこに足すかを書く（M の経路の表の説明と同じ。Stage 1 の目次案と一緒に承認をもらう）。入口のファイルは「対象の文書」と `--mark --add` にも入れる
- 「試作」の節は空のまま（5 で埋める）。「対象外（規模 M）」と書かない
- ブリーフの `missing` が挙げた欠けている項目・仮定の項目は、規模の問いで聞かず、Stage 1 で案を作って承認の問いにまとめる
- タスク一覧の先頭に次の3行を足す（雛形の行はそのまま残す）

```markdown
- [ ] Stage 1（ブリーフの確定・目次案・受け入れ基準・読者役による目次の点検）
- [ ] 試作（代表の節・いちばん難しい節・要素ごとの断片）
- [ ] 試作の見本を改訂設計書に残し、試作のファイルを消す
```

## 2. Stage 1

**症状が無い改訂（「なんとなく分かりにくい」）なら、Stage 1 の前に、今の本文で読者役レビューを1回まわす**（`manual-writer` の Step 6 と同じ渡し方。ただし改訂の範囲は渡さない。症状を探す段階なので、文書全体が範囲）。返ってきた指摘を症状として改訂設計書の「症状」に書き、目次案と受け入れ基準の根拠にする。確認の回数は増えない。

| すること | 中身 |
|---|---|
| ブリーフを確定する | `brief.mjs missing` の「欠けている項目」と「仮定」を、書き手が案を作って埋める。仮定を残さない |
| 目次案 | 文書群の全体なら、文書ごとの目次（見出しの並び）。先に `show.mjs reference structure` と `reference web` を出力して読む。節ごとに図・画面を付けるか（既定は「なし」。M の経路の目次案と同じ） |
| 受け入れ基準 | 文書ごとに3〜5個。今回の改訂の基準も書く（読者役の判定の基準になるので、ここで必ず決める） |
| **読者役による目次の点検** | 目次案と受け入れ基準を `doc-reviewer` に渡し、「この目次で基準を満たせるか」を見てもらう（下）。本文を書く前なので安い |

### 2-1. 目次の段階の点検

`doc-reviewer` エージェントを `Agent` ツールで起動する。プロンプトには次を入れる。

- 「**目次の段階の点検**。本文はまだ無い。目次案と受け入れ基準だけで、読者がゴールに着けるかを判定する」
- 目次案（見出しの並びと、各節で書く中身の1行）と受け入れ基準を、プロンプトに**全文で貼る**（改訂設計書のパスを渡さない。読者役は改訂設計書を読めない）
- ブリーフ（`brief.mjs show` の出力）
- 読者プロファイル（`show.mjs profile <名前>` の出力）
- 文書の種類で決まる必須見出し（`manual-writer` の Step 6 と同じ取り方）。目次案の見出しの名前を、検査に必要な語から変える指摘を出させない

返ってきた指摘（足りない節・順番・基準を満たせない目次）を目次案に反映し、改訂設計書の「目次案」と「問い合わせ」に書く。見送る指摘は理由を書く。

## 3. Stage 1 の承認（2回目）

ブリーフの案・目次案・受け入れ基準・読者役の点検で直したことを、**問いの直前の出力に全部書いてから**、1回で承認をもらう。

- 選択肢は「この Stage 1 で試作に進む（推奨）」「直す（どこを）」
- 承認されたら、ブリーフに書く（`apply.mjs --brief`。依頼者が決めた値は `"by":"依頼者"`）。改訂設計書の表の「承認」に日付と承認者を書く

## 4. 試作

**全体を書く前に、調子と方針を一部で見せて合意する。** 書き手が範囲を選ぶが、選び方を縛る（都合のよい段落だけで合意すると、全体を直したときに崩れる）。

| 選ぶもの | 理由 |
|---|---|
| 代表の1節 | 全体の調子が分かる |
| いちばん難しい1節 | 方針が通用するかが分かる |
| 要素ごとの断片（手順・警告・表・エラーへの対処・よくある質問のうち、文書にあるもの） | 地の文だけで合意すると、全体で崩れやすいのはこれら |

選んだ理由を1行ずつ添える。

**試作のファイル**は、元の文書の隣に `<元の名前>.proto-1.<拡張子>` で置く（`docs/usage/phone.html` なら `docs/usage/phone.proto-1.html`）。

- 既存の文書の改訂: 元の文書を写し、選んだ節だけを書き換える。HTML の CSS・画像・隣のページへの相対パスがそのまま効く
- 新規作成: 選んだ節だけを書いた短い文書にする（ほかの節は見出しだけ）
- 名前に `.proto-` が入ったファイルは、検査（`check-docs`・完了処理・コミット時の検査）の対象にならない。**承認の後に必ず消す**（残っていると完了処理の検査が止める）
- **2案は、方針が決まっていないときだけ**（「もっとやさしく」のような漠然とした依頼）。`.proto-1` と `.proto-2` にする。毎回2案は作らない

## 5. 試作の承認（3回目）

今と試作を並べて見せる。

- **並べ方**: 既存の文書の改訂なら、今の文と試作の文を節ごとに並べて出力する。HTML なら、元の文書と試作のファイルのパスを示し、ブラウザーで並べて開けることを伝える
- **比べる軸を添える**: 「どちらが綺麗か」ではなく、ブリーフの読者がつまずく点（プロファイルの観点）と症状に照らして、何が良くなったか
- 選択肢は「この方針で全体を書く（推奨）」「調整する（どこを）」「やめる」。**合意するまで全体に進まない**
- **調整する**: 試作を作り直して、もう一度見せる。**作り直しは同じ問いの続きとして扱い、確認の回数に数えない**（試作を合わせ込むのは自然なやりとりで、回数で縛ると窮屈になる）。**調整は2回まで**（何回目の調整かを、改訂設計書の「試作」の節の「判定」に書く）。 3回目の調整を求められたら、方針そのものが合っていない兆候なので、作り直さずに「今の試作で進める」「やめる」「方針から決め直す」から選んでもらう（方針から決め直すなら Stage 1 に戻り、新しい依頼として回数を数え直す）
- **やめる**: 試作のファイルを消し、改訂設計書の状態を「中止」にして `completed/` に移し、`complete-doc.mjs --clear` で基準点を消す。記録は書かない（文書は変わっていない）。Stage 1 でブリーフに書いた値は残る（承認済みの決め事なので）
- **文体（文末・語りかけ）を今の `voice.md` から変える試作なら**、そう明記する。採用なら完了前の確認で `voice.md` に書くかを聞く（finish の 3-1）。文末を変えるなら、テイスト変更の経路（`show.mjs path tone`）の 4-2 と同じく、全体を書く前に文末の検査を止める

承認されたら:

1. 承認した試作の文を、改訂設計書の「試作」の節に写す（範囲・選んだ理由・案・判定）。**これが全体を書くときの見本になる**
2. 試作のファイルを消す
3. 改訂設計書のタスク一覧の、Stage 1 と試作の行にチェックを付ける

## 5-1. 端末でしか確かめられない事実を、書き始める前に確かめる

OS が出す画面の文言・権限の確認の数・端末の設定の道筋のように、実機・エミュレーターでしか確かめられない事実があれば、**全体を書く前にまとめて確かめる**（実地検証で、メインが書きながら直列で確かめたため、先に起動した書き手が端末の事実を知らずに書き、メインの文脈が画像と出力で膨らんで圧縮された）。

- 確認は、**確認専用のサブエージェントに任せる**（メインの文脈を守るため）。指示には、確かめる事実の一覧と、`show.mjs writer-handoff` の「事実の確認」の節（**実行する前に止まる操作**を含む。緊急番号に発信しない・`adb` は `-s` で端末を指定する）を全文で入れる。サブエージェントは依頼者に聞けないので、**止まる操作は実行せず、一覧で返させる**
- 結果（文言・手順・画像のパス）は、改訂設計書の「事実の確認」と問い合わせ表に書かせる
- 書き手のエージェントは、この結果が出てから起動する
- 確認のために作ったもの（エミュレーター・画像・端末の言語の設定）は、完了報告の「確認のために作ったもの」に書く

## 6. manual-writer に渡す

M の経路の「3. manual-writer に渡す」と同じ。添えるものに次を足す。

- 「試作の見本は改訂設計書の『試作』の節にある。全体はこの見本に揃える。並列のエージェントに書かせるときは、改訂設計書のパスと `show.mjs writer-handoff` の出力を全文で渡す」

`manual-writer` は改訂設計書があれば Step 1 の問いと Step 3 の承認を省き、最後に `show.mjs path finish` を読んで終える。
