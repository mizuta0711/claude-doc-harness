# plan-doc の経路: S（小さな修正）

規模 S と承認されたら、この手順で最後まで進める。設計書・目次案・読者役レビューを省く。**省かないのは次のこと。**
`${CLAUDE_SKILL_DIR}` は plan-doc のフォルダー（絶対パスに置き換えて書く）。

1. **事実を確かめる。** `manual-writer` の Step 2 と同じ（実物で確かめる・実行する前に止まる操作・出力を写すときに伏せるもの）。
   画面名・ボタン名は、その画面を描いているソース（UI の文字列リソースがあればそれ）か実物で確かめる。プロジェクト全体から文字列を集めない
   確かめられなかった事実は、本文に「未確認」と書かず、本文のその箇所に問い合わせの印（`<!-- 問い合わせ: Q1 -->`。番号だけ）を置き、完了報告の「問い合わせ」に書く
2. **直す。** `docs-style/voice.md` とブリーフの「文体の差分」に沿って書く。**書き換えは `Edit` で行う**（Bash の python や sed で書き換えると、検査のフックが働かず、改行コードも崩れやすい。実地検証で両方起きた）。
   読者向けの改訂履歴の行は、承認の後（4 の後）に書く
3. **同じ記述を、ほかの文書でも探す（横展開）。** 直した事実と同じ記述を、検査対象の全文書から `Grep` で探す。
   見つかったら一覧にし、完了報告の問いで「まとめて直すか・依頼者に回すか」を聞く。
   - **同じ事実を同じ書き方で直すだけなら、本数が増えても S のまま**（承認の問いに含め、記録は1節にまとめる。1節にまとめるときは `doc` ではなく `docs` に全部の文書を並べる。並べないと、完了処理の検査が文書ごとに節を探して NG を出す）
   - 直す文書が増えたら、`complete-doc.mjs --mark --add <増えた文書>` で基準点に足し、**直す前に `history.mjs show <増えた文書>` で経緯を読む**（その文書にだけ残っている改訂意図に反して直さないように）
   - 横展開の先が別の文書群（ブリーフ）なら、記録は文書群ごとに1節ずつ書く（`history.mjs add` は文書群をまたぐ節を書かない）
   - ほかの文書で書き方まで変える必要がある（前後の手順が違う・読者が違う）なら、規模を M に判定し直す
4. **書いた後の条件を見る。** 直した文書の前後を比べる

   ```bash
   node "${CLAUDE_SKILL_DIR}/../../scripts/complete-doc.mjs" compare <直した文書のパス...>
   ```

   「前後確認を必須にする」と出たら（本文の字数が 1.5 倍以上か 0.67 倍以下）、5 の問いに前後確認（`compare` の結果と、事実の変更の一覧）を含める
5. **確かめることがあれば、ここで1回だけ聞く（記録を書く前）。** 事実を変えた・横展開が見つかった・用語を足したい・問い合わせがある・4 で条件に当たった、のどれかがあれば、
   完了報告の案（下の表）を示して承認をもらう。事実の変更は一覧（箇所・前・後・根拠）で**問いの本文か直前の出力に**見せ、1件ずつ外せるようにする。作業中に依頼者が「覚えておいて」と言ったことがあれば、書き戻すかも同じ問いで聞く。
   **答えを本文に反映してから、記録を書く**（記録は追記だけで、書いた節は後から直さない。承認の前に書くと、外された事実の変更が記録に残る）。
   どれも無ければ聞かない
6. **改訂の記録を残す。**
   - 内部の改訂記録に1節（必須）。改訂意図は空にしない（誤字の修正なら「誤字の修正」）。「変更者・承認者」は、承認をもらった人を書く

     ```bash
     node "${CLAUDE_SKILL_DIR}/../../scripts/history.mjs" add --json '{"docs":["docs/usage/phone.md","docs/usage/index.md"],"size":"S","改訂箇所":"phone.md の手順3・index.md の「はじめて使うとき」（横展開）","改訂内容":"許可を求められる時期を「初めて発信を押したとき」から「初回起動時にまとめて」に直した","改訂意図":"実装と違っていた。読者が見慣れない許可の画面に戸惑わないように","根拠":"MainActivity.kt:168-181","読者向けの改訂履歴":"手順3：電話の許可を求められる時期の説明を直しました","変更者・承認者":"Claude・依頼者","改訂設計書":"なし"}'
     ```

   - ブリーフで読者向けの改訂履歴が「あり」なら、文書の「改訂履歴」の節に1行（ブリーフの「置き場所」がまとめのページのパスなら、そのページに1行。ページも変わった文書なので、上の `history.mjs add` の `docs` に入れる。いつ・どこを・どう変えたかを、読者向けの言葉で簡潔に。改訂意図は書かない）。
     節が無ければ、`voice.md` の「読者向けの改訂履歴」に従って文書の末尾に作る
7. **完了処理の検査を通す。**

   ```bash
   node "${CLAUDE_SKILL_DIR}/../../scripts/complete-doc.mjs" <直した文書のパス（横展開の先も含めて全部）>
   ```

   `NG` が出たら直す。ただし「判定できない」（基準点が無い）は直そうとせず、完了報告にそう書き、今回足した記録の節を示す。問い合わせの印を残したまま渡すなら `--allow-queries` を付け、完了報告にそう書く

## 完了報告

| 項目 | 内容 |
|---|---|
| 文書 | パス |
| 性質と規模 | 承認したもの（**規模を必ず書く**。記録に書いた規模と、依頼者が承認した規模を照らせるように） |
| 変えたこと | 改訂箇所と改訂内容。**事実を変えたときは、前・後・根拠（ファイルと行）** |
| 横展開 | 同じ記述が見つかった文書と箇所（無ければ「なし」） |
| 問い合わせ | 確かめられなかった事実と、本文の印の番号。無ければ「なし」。**行を省かない** |
| 改訂の記録 | 内部の改訂記録に足した節・読者向けの改訂履歴に書いた1行 |
| 完了処理の検査 | `complete-doc.mjs` の結果 |
| 文書の外で見つかった問題 | 製品の不具合・ほかの文書の誤り（あれば） |
| 依頼者が次にやること | 問い合わせへの回答・公開の操作（あれば）。**この作業の変更だけでコミットする**（前の作業とまとめてコミットすると、コミット時の検査が作業ごとの記録を見分けられない） |

完了報告は、5 の問いの答えを反映し、記録と検査を済ませた後に出す。**ここでは新しく問わない。**
