# plan-doc の経路: テイスト変更（M・L）

テイスト変更（事実と構成を変えず、文体・表記・見た目だけを変える）と判定したら、規模によらずこの手順で進める。
規模は、1本の短い文書なら M、2本以上か、長い1本（要素の種類が多く、代表の1節だけでは調子を決めきれない）なら L。
**どちらも試作から始め、Stage 1（目次案）は通らない**（構成を変えないので、目次案に意味が無い）。
`${CLAUDE_SKILL_DIR}` は plan-doc のフォルダー（絶対パスに置き換えて書く）。

**確認の回数は M で3回・L で4回まで**（規模と前提 → 試作 → 完了前の確認。L は試作の調整に1回の余りがある）。

## 1. 改訂設計書を作る

雛形（`show.mjs plan-template`）から `docs-style/plans/YYYYMMDD_<名前>.md` に `Write` で書く。埋め方は次の表で全部（M の経路は読まなくてよい）。

| 節 | 埋め方 |
|---|---|
| 表 | 状態は「作業中」。性質と規模は「テイスト変更・M」か「テイスト変更・L」。対象の文書は全部（バッククォートで囲む。コミット時の検査がこの一覧を読む） |
| 症状 | 依頼のきっかけ（「家族が硬いと言っている」）。無ければ「なし」 |
| 受け入れ基準 | 「文書の基準」は `- [ ] 対象外（テイスト変更。中身を変えないので、文書の基準は変わらない）` の1行だけにする。「今回の改訂の基準」に下の既定を書く（Stage 1 を通らないので、既定を置く） |
| 改訂方針 | 何を変えるか（文体・表記・見た目のどれか）、どう変えるか、書く先（下の 4-1）、文末の検査の今の値（下の 4-2）、変えないもの（下の 3 の表） |
| 目次案 | 「変えない（テイスト変更）」と1行書く |
| 試作 | 空のまま（4 で埋める） |
| タスク一覧 | 雛形の行を消し、下のタスクに置き換える |

テイスト変更の受け入れ基準（既定）:

```markdown
- [ ] 事実・数値・手順の順番と数・画面名・コードが、git diff で変わっていない
- [ ] 承認した試作の調子に沿っている（読者役が試作の見本と比べて判定する）
- [ ] 一部の文書群だけ変えたときは、ほかの文書群の文書が変わっていない
```

タスク一覧:

```markdown
- [ ] 試作（M は代表の1節。L は代表の節・いちばん難しい節・要素ごとの断片）
- [ ] 試作の見本を改訂設計書に残し、試作のファイルを消す
- [ ] 書き換える（change-tone）
- [ ] 中身が変わっていないことを git diff で確かめる
- [ ] 読者役が見本と比べて点検する
- [ ] 前後確認を書く
- [ ] 完了前の確認（voice.md・ブリーフの「文体の差分」を書くかも同じ問いで）
- [ ] 完了処理（設計書を completed/ へ・voice.md の更新・記録・改訂履歴・complete-doc）
```

**見た目だけの変更（CSS の値だけで、文書の本文は変わらない）も記録を書く。** 内部の改訂記録の `docs` には、その CSS を読み込む文書を並べる。
ただし文書が変わらないので、完了処理の検査とコミット時の検査は働かない（検査は文書の変更を起点にするため）。完了報告にそう書く。

## 2. 何を、どう変えるかを決める

依頼文から読み取る。読み取れないことは聞かず、案を作って試作で見せる（問いを増やさない）。

- **何を**: 文体（文末・温度・専門用語・一文の長さ）、表記（長音・数字・用語の統一）、見た目（HTML だけ。文字の大きさ・配色・余白）
- **どう**: 依頼文が具体的（「です・ます調に」）なら、`docs-style/voice.md` の項目に当てはめる。漠然としている（「もっとやさしく」）なら、文体の見本集（`show.mjs voices`）から近いものを選んで試作にする。**このときだけ2案まで**
- 見た目を変えるときは、既存の CSS を読み、変える値（変数や該当のセレクター）と変更前→変更後の値を表にする。見た目の方向性（`show.mjs visuals`）の「どの方向性でも守ること」（コントラスト比 4.5:1 以上ほか）を下回る変更は、理由を添えて止める

## 3. 試作

| 規模 | 試作の範囲 |
|---|---|
| M | 代表の1節 |
| L | 代表の1節・いちばん難しい1節・要素ごとの断片（手順・警告・表・エラーへの対処・よくある質問のうち、文書にあるもの）。選んだ理由を1行ずつ |

試作のファイルは、元の文書の隣に `<元の名前>.proto-1.<拡張子>` で置く。元の文書を写し、選んだ節だけを書き換える（HTML の CSS・画像・相対パスがそのまま効く）。見た目の変更なら、CSS の値を変えた写しを `<元の CSS の名前>.proto-1.css` にし、試作のファイルからそれを読む。
この形の名前（`.proto-` と数字）のファイルは、検査の対象にならない。**承認の後か、やめると決めたときに必ず消す**（残っていると完了処理の検査が止め、コミットしようとするとコミット時の検査が止める）。

**試作を作っていて、前提や用語の説明を足さないと読者に届かないと分かったら、テイスト変更ではない。** 言い回しだけをやさしくしても、前提が抜けたまま残る。
改訂として規模 L に判定し直す。改訂設計書の性質と規模を「改訂・L」に、受け入れ基準とタスク一覧を L の経路（`show.mjs path L`）のものに入れ替え、L の Stage 1 から進める。
**判定し直しの承認は、L の Stage 1 の承認の問いにまとめる**（「テイスト変更のつもりだったが、〇〇の説明が要るので改訂として直す」と添える）。作った試作は、L の試作で使い回す。確認は L の4回に収まる。

書き換えで守ること（試作でも全体でも同じ）:

| 変えてよい | 変えない |
|---|---|
| 文末・語尾、言い回し、語りかけ、文の区切り（長い文を2つに分ける） | 書いてある事実・数値・手順の順番と数 |
| 専門用語の言い換え（用語集にあるものは用語集に従う） | 画面名・ボタン名・コマンド・コード・ファイル名 |
| 表記（長音・数字） | 見出しの構成、リンク先、画像 |
| HTML: 本文のテキスト・CSS の値 | HTML: タグの構造・クラス名・属性 |

## 4. 試作の承認（2回目）

今の文と試作の文を、節ごとに並べて**問いの直前の出力に**示す。HTML なら元の文書と試作のファイルのパスも示し、ブラウザーで並べて開けることを伝える。見た目を変えるなら CSS の値の表も同じ問いで示す。

```text
【今】  設定は config.json に保存する。保存後の再起動は不要である。
【試作】設定は config.json というファイルに保存されます。保存したあと、再起動する必要はありません。
```

- 比べる軸を添える（ブリーフの読者がつまずく点に照らして、何が良くなったか）
- 変更の規模（対象の本数・おおよその変更箇所数）も添える
- 改訂設計書の受け入れ基準と改訂方針の承認も、同じ問いで取る（問いを増やさない）
- 選択肢は「この調子で全体を変える（推奨）」「調整する（どこを）」「やめる」。**合意するまで書き換えに進まない**
- **調整する**: 試作を作り直して、もう一度見せる。確認の回数に数える。上限（M 3・L 4）に達するなら、もう一度見せる前に「次に見せると上限を超える」と添え、「調整して見せる」「今の試作で進める」「やめる」から選んでもらう
- **やめる**: 試作のファイルを消し、改訂設計書の状態を「中止」にして `completed/` に移し、`complete-doc.mjs --clear` で基準点を消す。記録は書かない（文書は変わっていない）。4-2 で文末の検査を止めていたら、元の値に戻す

承認されたら:

1. 承認した試作の文（と CSS の値の表）を、改訂設計書の「試作」の節に写す。**これが全体を書き換えるときの見本になる**
2. 試作のファイルを消す
3. 改訂設計書の表の「承認」に日付と承認者を書き、タスク一覧の試作の2行にチェックを付ける

### 4-1. voice.md はまだ書かない

**`docs-style/voice.md`（とブリーフの「文体の差分」）は、完了前の確認で採用が決まってから書く**（`show.mjs path finish` の 3-1）。
試作の承認の時点で書くと、全体を直した後に「やり直す」となったときに、決まりだけが変わったまま残る。
中断しても何に揃えるかは、改訂設計書の「試作」の節に残っている。

改訂方針の「書く先」には、どちらに書くかを今決めて書いておく。

| 対象 | 書く先 |
|---|---|
| 検査対象の全体（プロジェクトのすべての文書群） | `docs-style/voice.md` |
| 一部の文書群だけ | その文書群のブリーフの「文体の差分」。`voice.md` は変えない（変えると、触らなかった文書群の文書がその時点で決まり違反になる） |

### 4-2. 文末を変えるときは、書き換えの前に文末の検査を止める

`voice.endings`（文末の機械の検査）は、`voice.md` と同じく完了前の確認の後に書く。そのままでは、書き換えのたびに `check-docs` フックが新しい文末を「混在」として止める。

文末を変える（敬体と常体を入れ替える）ときだけ、**試作の承認の後、書き換えの前に**次をする。

1. 今の値を、改訂方針の「文末の検査の今の値」に書く。値は次で出す（`.claude/` 配下は `Read` しない）

   ```bash
   node -p "(require('./.claude/doc-harness.config.json').voice || {}).endings ?? null"
   ```
2. 文末の検査を止める

   ```bash
   node "${CLAUDE_SKILL_DIR}/../setup-project/scripts/apply.mjs" --config '{"voice":{"endings":null}}'
   ```

3. 完了前の確認で採用されたら、finish の 3-1 で新しい値を書く。「やり直す」「やめる」なら、1 で書いた元の値に戻す

## 5. change-tone に渡す

`/harness-doc:change-tone` を、改訂設計書のパスと承認した規模・前提を添えて呼ぶ。`change-tone` は書き換えと確かめをし、最後に `show.mjs path finish` を読んで終える。**plan-doc に戻ってこない。**
