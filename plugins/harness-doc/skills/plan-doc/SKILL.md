# plan-doc

**文書を書く・直す依頼は、まずここを通る。** 依頼の性質と規模で経路を分け、規模に合った工程だけを通す。

> **なぜ入口を1つにするか。** 経路ごとに入口のスキルを分けると、説明文が似て呼び分けを誤り、同じ工程が各スキルに複写されて
> 片方だけ直す事故が起きる。**入口で判断し、その後の経路を分ける。** 判断の基準は下の表で固定する。
>
> **なぜ規模で分けるか。** 数値1つの直しにも目次案と読者役レビューを通すと、利用者は「スキルを使わずに直して」と言い始め、
> ハーネスが迂回される。**全変更に重い手続きを課さない**（claude-dev-harness の規模ゲート原則と同じ）。

使うスクリプト（`${CLAUDE_SKILL_DIR}` は絶対パスに置き換えて書く）:

| 名前 | コマンド |
|---|---|
| ブリーフ（読者・扱わないこと） | `node "${CLAUDE_SKILL_DIR}/../../scripts/brief.mjs" show <文書のパス>`・`missing <文書のパス>` |
| 内部の改訂記録（これまでの経緯） | `node "${CLAUDE_SKILL_DIR}/../../scripts/history.mjs" show <文書のパス>` |
| 改訂の記録を足す | `node "${CLAUDE_SKILL_DIR}/../../scripts/history.mjs" add --json '<JSON>'`（本文に `'` が入るなら、JSON をファイルに書いて `--json-file <パス>`） |
| 完了処理の検査・前後の比較 | `node "${CLAUDE_SKILL_DIR}/../../scripts/complete-doc.mjs" <文書のパス...>`・`compare <文書のパス...>` |
| 経路の手順・改訂設計書の雛形 | `node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" path <S\|M>`・`plan-template` |
| ブリーフを書く・作る | `node "${CLAUDE_SKILL_DIR}/../setup-project/scripts/apply.mjs" --brief '<JSON>'` |
| CLAUDE.md の節の最新版 | `node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" claude-section` |

## Step 0: 導入済みかを確かめる

- `.claude/doc-harness.config.json` が無ければ、文書ハーネスを導入してから進めることを1行で伝え、了承を得て `/harness-doc:setup-project` を通す
- あれば、プロジェクトの `CLAUDE.md` の「文書ルール（harness-doc）」の節を、最新版（上の表）と比べる。**最新版と違えば**（どの規則でも。0.8.0 で導入したプロジェクトにも、続けての依頼の扱いのような新しい規則が届いていない）、
  またはブリーフが1つも無ければ、`/harness-doc:setup-project` の「導入済みのプロジェクトに足す」を1行で勧める。断られたら、そのまま進める（古い規則より、このスキルの手順を優先する）

`.claude/` 配下は `Read` も `Edit` もしない。上のスクリプトを通す。質問は `AskUserQuestion` で選択肢として出す（1回4問まで。推奨を先頭に「（推奨）」）。

## 確認の回数

**1回 = 問いを出し、依頼者の返事を待つ1往復。** 1往復に複数の問いと一覧を並べてよい。許可の確認と、安全のための止め所（破壊的な操作の前の確認）は数えない。

| 経路 | 依頼者の判断 | 上限 |
|---|---|---|
| S（完了時に聞くことが無い） | 規模と前提 | 1 |
| S（事実の変更・横展開・用語の追加がある） | 規模と前提 → 完了報告での承認 | 2 |
| M・L | 規模と前提 → 改訂設計書（受け入れ基準と目次案）→ 完了前の確認 | M 3・L 4（L の残りの1回は次の版の試作） |

**作業の途中で聞きたくなったことは、その場で聞かず、完了報告の問いにまとめる。** 書き進められないほどの食い違いだけは例外。

### 問いの書き方（どの問いにも当てはめる）

- **承認を求める中身は、問いの本文（`AskUserQuestion` の `question` か選択肢の説明・プレビュー）か、問いの直前の出力に全部書く。** 思考の中に書いても依頼者には見えない。
  見えない案を「この案で進めてよいですか」と聞かない（実地検証で、ブリーフの案の中身が見えないまま承認を求めた）
- **改訂記録やブリーフを読んで分かったことを理由にするなら、そのことも書く**（「改訂記録の 2026-10-04 の節に『実装と違っていた』とあります」）。読んだのに黙って結論だけ聞かない
- **推奨の選択肢は、読者の害で選ぶ。** ブリーフの読者像と読者プロファイルの「つまずく点」を当て、読者が誤操作をする案・画面と合わない案を推奨にしない（実地検証で、画面の文言を言い換える案と、動かない機能を黙っておく案が推奨になった）

## Step 1: 受付 — 性質と経緯を確かめる

### 1-1. 性質

| 性質 | 見分け方 | 次 |
|---|---|---|
| 新規作成 | 対象のファイルが無い | 規模判定（新規は M 以上） |
| 改訂 | 既存の文書を、伝わるように直す | 症状を確かめてから規模判定 |
| 誤りの修正 | 事実が違うと分かっている | どこが・何と違うかを確かめてから規模判定 |
| テイスト変更 | 事実と構成を変えず、文体・表記・見た目だけを変える | 規模判定。**前提や用語の説明を足さないと読者に届かないなら、改訂として扱う** |
| 方針変更 | 読者・扱わないこと・事実の承認者・読者向けの改訂履歴の有無を変える | `/harness-doc:change-policy` へ渡して終える |
| 点検だけ | 読者役のレビューだけを頼まれた | `doc-reviewer` を起動して終える |

### 1-2. 症状（改訂・誤りの修正のとき）

**誰が・どの箇所で・何をしようとして困ったか**を、依頼文から読み取る。読み取れなければ、規模の承認の問いで一緒に聞く。
「なんとなく分かりにくい」で症状が無ければ、規模を L と推測し、渡した先で読者役レビューを先にかけて症状を作る。
原因が中身か・調子か・入口（辿り着けない）か・製品の不具合かを、ここで見当を付ける。

### 1-3. 前提と経緯を読む

対象の文書のパスで、ブリーフと内部の改訂記録を引く。

```bash
node "${CLAUDE_SKILL_DIR}/../../scripts/brief.mjs" show <文書のパス>
node "${CLAUDE_SKILL_DIR}/../../scripts/brief.mjs" missing <文書のパス>
node "${CLAUDE_SKILL_DIR}/../../scripts/history.mjs" show <文書のパス>
```

- **依頼が過去の決定と食い違うとき**（ブリーフの「扱わないこと」や、記録の改訂意図・見送ったことに反する依頼）は、規模の承認の問いで一言添える。
  例:「前回、端末 OS の設定は扱わないと決めています（2026-10-05 の改訂）。今回は扱いますか」。黙ってどちらかに寄せない
- ブリーフが無い場所なら、プロジェクトにブリーフが1つも無いとき（`brief.mjs list` が空）は `/harness-doc:setup-project` の「導入済みのプロジェクトに足す」を勧める。
  ブリーフはあるがこの場所に無いなら、規模の承認の問いで一緒に確かめてから作る。**README のように1本だけの文書は、文書群 `default` に入れる**（`paths` にそのファイルを足す）。
  新しい文書群なら、名前（英数字）・文書群の名前・`paths`・読者の案を示す。作るときは:

  ```bash
  node "${CLAUDE_SKILL_DIR}/../setup-project/scripts/apply.mjs" --brief '{"name":"default","title":"どの文書群にも入らない文書","paths":["README.md"],"by":"依頼者","set":{"読者":{"プロファイル":"developer","読者像":"このリポジトリを初めて見る開発者"},"読者向けの改訂履歴":{"読者向けの改訂履歴":"あり"}},"outOfScope":["なし"]}'
  node "${CLAUDE_SKILL_DIR}/../../scripts/history.mjs" init default
  ```

  ブリーフが無いと内部の改訂記録の置き場所が決まらず、改訂の記録を書けない（`history.mjs add` が止まる）

### 1-4. 作業前の基準点を記録する

**文書に手を付ける前に**、完了処理の検査が比べる基準点を記録する。依頼者が作業のあいだにコミットを挟むとは限らず、基準点が無いと、前の作業で足した記録で今の作業が合格してしまう。

```bash
node "${CLAUDE_SKILL_DIR}/../../scripts/complete-doc.mjs" --mark <直す・作る文書のパス...>
```

作業の途中で直す文書が増えたら（目次・ページ送り・横展開で見つかった別の文書）、`--mark --add <増えた文書のパス>` で足す（既に記録した文書は上書きされない）。
渡した先のスキル（manual-writer・change-tone）がもう一度 `--mark` しても、同じコミットの上で、まだ改訂の記録を書いていなければ上書きせずに足すので、直した後の中身が「作業前」にはならない。
前の作業が残した基準点（記録まで書いた・検査を通った）には足さず、作り直す。

**何も変えずに作業を終えたら**（依頼者が「戻さない。今のままでいい」と答えた・点検だけで終わった）、基準点を消す。残すと、次の作業が古い基準点と比べてしまう。

```bash
node "${CLAUDE_SKILL_DIR}/../../scripts/complete-doc.mjs" --clear
```

## Step 2: 規模を判定する

**受付の時点で分かる軸だけで決める。** 字数の増え方や事実の変更の件数は、書いた後でないと分からない。

| 規模 | 目安（どれか1つでも当たれば上の規模） |
|---|---|
| S | 1本・見出しを変えない・直す事実が分かっていて1か所以内 |
| M | 見出しを増減する、直す事実が2か所以上、新規の1本、1本のテイスト変更、図・画面を足す・替える。読者は変えない |
| L | 新規の文書群・読者の変更・2本以上にまたがる（テイスト変更を含む）・「分かりにくいので直して」のように範囲が決まっていない改訂 |

- **AI が推測し、依頼者が承認する。迷ったら上の規模で出す**（AI は楽な方に倒れやすい）
- **規模の承認は、前提の提示と1回の問いにまとめる。** ブリーフの `missing` が挙げた「欠けている項目」「仮定の項目」も同じ問いで聞く。
  **ただし S では、その修正に要る項目だけを聞く**（ほとんどの場合は聞かない。読者向けの改訂履歴の有無が欠けているときだけ聞く、のように）。M・L で項目が4つを超えるなら、案を表で示して承認か修正をもらう形にする（`AskUserQuestion` は1回4問まで）

```text
この依頼は「誤りの修正・規模 S」と判断しました（1本・見出しは変えない・直す事実は手順3の1か所）。
前提: 読者 = 初めて使うシニア ／ 扱わないこと = 端末 OS の設定
この判定で進めてよいですか
```

**この「前提: …」の行は、必ず問いの本文（`question`）に入れる。** 規模 S でも省かない。途中の出力や思考に書いても、依頼者に見えないことがある（実地検証で、plan-doc は4回の作業のどれでも前提の行を依頼者に見せていなかった）。

- 作業中に膨らんだら（S のはずが同じ誤りが3本にあった）、**判定に戻る**

## Step 3: 経路を分け、経路の手順を読む

**経路の手順はこのファイルに書いていない。** 判定したら、次のコマンドで経路の手順を出力して読み、それに従う（`Read` で開かない。プラグインはプロジェクトの外にあり、確認が出たり拒否されたりする）。

| 規模と性質 | 経路 | 読むもの |
|---|---|---|
| S | このスキルの中で最後まで進める | `node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" path S` |
| M・L の新規作成・改訂・誤りの修正 | 改訂設計書を作って承認を取り、`/harness-doc:manual-writer` に渡す | `node "${CLAUDE_SKILL_DIR}/../../presets/show.mjs" path M` |
| M・L のテイスト変更 | `/harness-doc:change-tone` に渡す（規模・承認した前提・症状・経緯の要点を添える） | — |

> 規模 L の Stage 1（目次の段階の読者役の点検）と試作、テイスト変更を試作から始める形は、次の版で入る。いまは L も M の経路（改訂設計書）を通す。

**経路を読まずに進めない。** 同じセッションで前に読んだことがあっても、依頼ごとに読み直す（実地検証で、続けての依頼では手順を覚えている範囲で進め、記録が抜けた）。

## コミット時の検査

文書を含むコミットは、コミットの時点でフックが改訂の記録を確かめ、無ければ止める（スキルを通らなかった作業も止まる）。

- 止められたら、記録を足してからコミットし直す。**コミットの文言に `doc-record: skip（理由）` を書いて外そうとしない**（書くと依頼者の承認を求める問いが出る。harness-doc の工程を通さない正当な変更のときだけ、依頼者にそう説明して使う）
- `git add` と `git commit` を1つのコマンドでつないでよい（フックがコミットの中身を再現して確かめる）。ただし commit より前にファイルを書き換えるコマンドを置くと、確かめられないので止まる
