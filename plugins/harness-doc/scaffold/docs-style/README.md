# 文書ハーネスの使い方

<!-- doc-type: howto -->

## この文書でできること

Claude Code にマニュアル・手順書・仕様書を書かせるとき、**毎回同じ手順・同じ水準**で
書かせ、予備知識のない読者役のレビューと機械チェックを通した状態で受け取れるようになる。
**利用者はコマンドを打たない。** Claude Code に日本語で頼むだけでよい。

読者: このプロジェクトで Claude Code に文書を書かせる人。

## 前提条件

- このプロジェクトに文書ハーネスが導入されている（この `docs-style/` フォルダがあれば導入済み）
- 書かせたい文書が検査対象に入っている。検査対象は `.claude/doc-harness.config.json` の
  `include`（対象）と `exclude`（対象外）で決まる。claude-dev-harness を併用しているプロジェクトでは、
  `docs/設計書/`・`docs/features/`・`docs/reviews/`・`docs/handoff/` は対象外で、従来どおり harness-core が扱う

## 手順

### 1. 何を、誰のために書くかを伝える

Claude Code に次のように頼む。**読者**と**読み終えたら何ができるべきか**を添えると、質問が減る。

```text
障害時の復旧手順書を書いて。読者は運用担当。読み終えたらサービスを再起動して正常を確認できるようにしたい
```

既存の文書を直すときも同じ。

```text
docs/利用マニュアル/ログイン.md を、初めて使う人が迷わないように書き直して
```

期待される動き: `plan-doc` スキルが依頼の大きさ（規模 S・M・L）と前提（読者・扱わないこと）を1〜2行で示して確かめてくる。
数値1つの直しのような小さな修正（S）は、そのまま直して終わる。新しい手順書や大きな書き直し（M・L）は、次の 2 に進む。

### 2. 改訂設計書を確かめる（M・L）

Claude は、受け入れ基準（「読者が文書だけで〇〇できる」を3〜5個）と目次案を書いた改訂設計書（`docs-style/plans/`）を作って見せてくる。

期待される動き: 目次案が「読者がやりたいこと」の順になっているか、基準が読者のゴールに合っているかを見て、違えばここで伝える。
承認すると、`manual-writer` スキルが対象のコード・設定を読み、手順に出るコマンドを実行してから本文を書く。
確かめられなかった事実は「問い合わせ」に挙がる（本文では断定しない）。

### 3. 本文が書かれ、`check-docs` フックが走る

文書を書くたびにフックが曖昧語・見出し・言語指定・用語集・リンク切れを検査する。

期待される動き: 違反があると次のような指摘が出て、Claude がその場で直す。利用者の操作は要らない。

```text
[check-docs] docs/guide/復旧手順.md に 2 件の指摘があります。直してから先へ進んでください。
  L12  曖昧語「適宜」: 条件と値を具体的に書く
  L30  コードブロックに言語指定がありません（例: ```bash、```text）
```

### 4. 読者役レビューの結果を見る

`doc-reviewer` エージェントが、文書だけを頼りに作業できるかを点検して指摘を返す。

期待される動き: 指摘ごとに「場所・問題・読者がどう困るか・修正案・重大度」が並び、
スキルが全件に「対応済み／見送り（理由）」を付けて本文へ反映する。

### 5. 完了前の確認に答える（M・L）

書き上がると、Claude が1回だけ確かめてくる。既存の文書を直したときは、前と後の比べ（本文の字数・見出しの増減・事実の変更の一覧）が並ぶ。
確かめられなかった事実（問い合わせ）も同じ問いに並ぶ。

期待される動き: 「このまま採用」「一部を戻す」「やり直す」から選ぶ。採用すると、改訂の記録（内部の記録と、読者向けの改訂履歴の1行）が残り、最後に完了報告の表が出る。
「やり直す」を選ぶと、文書を作業を始める前の中身に戻す（作業中に自分で直した分も消えるので、そのことを確かめてくる）。

### 6. コミットする

Claude にコミットを頼むと、コミットの前にフックが改訂の記録を確かめる。記録の無い文書を含むと、コミットが止まり、Claude が記録を足してからやり直す。
**1つの作業ごとにコミットする。** 前の作業とまとめてコミットすると、どの記録がどの作業のものか見分けられない。

### 7. テイストを変えたいとき

文体や見た目を変えたいときは、そう頼む。

```text
使い方のページを、もっとやさしい言葉に変えて
```

期待される動き: `change-tone` スキルが、今の文と変えた後の文を並べて見せてくる。
「この調子で全体を変える」を選ぶと、書いてある事実や手順は変えずに言い回しだけを書き換え、
`docs-style/voice.md`（この文書群の文体の決まり）も更新する。

### 8. 読者や扱う範囲を変えたいとき

文書群ごとの読者と扱わないことは、ブリーフ（`.claude/rules/doc-brief-*.md`）に残っている。変えたいときは、そう頼む。

```text
使い方のページの対象読者を、手伝う家族に変えたい
```

期待される動き: `plan-doc` が方針の変更と判定して `change-policy` スキルに渡し、新しい決め事の案と、それに合わなくなる文書の一覧を見せてくる。
直し方（言い回しだけ直すか、中身から直すか）が文書ごとに振り分けられ、今すぐ直すか後で直すかを聞かれる。

## 確認

完了報告の表で次を確かめる。

- 「読者とゴール」が、頼んだ内容と合っている
- 「機械チェック」が通過になっている
- 「読者役レビュー」の致命的・要修正が、すべて対応済みになっている
- 「問い合わせ」に挙がった項目があれば、自分で確かめるか、確かめられる人に回す。結果を伝えれば本文を直す
- 「完了処理の検査」が OK になっている（改訂の記録が残っている）

## うまくいかない場合

| 症状 | 原因 | 対処 |
|---|---|---|
| 頼んでもスキルが起動せず、Claude がそのまま書き始める | 依頼文から文書作成だと判断されなかった | 「plan-doc で」と添えて頼み直す |
| 「このプロジェクトに文書ハーネスを導入してから書きます」と聞かれる | このプロジェクトにはまだ導入されていない | 了承すると `setup-project` スキルが導入してから書き始める |
| 設計書を頼んだら「対象外」と言われる | claude-dev-harness の設計書は harness-core が扱う | 設計書は従来どおり `update-docs` のような harness-core のスキルで頼む |
| 検査してほしくない文書でフックが止める | その文書が `include` に当たっている | 「この文書を検査対象から外して」と頼む。Claude が `exclude` に足す |
| 曖昧語の説明のために曖昧語そのものを書きたい | 本文に書くと検出される | Markdown ならインラインコード（`` `適宜` ``）、HTML なら `<code>` で囲めば検査しない。Claude に「語の説明なのでコードとして囲んで」と伝える |
| 用語集の禁止表記が固有名詞に当たる | 例: 製品名に「サーバ」を含む | その行末に `<!-- check-docs: ignore 理由 -->` を書く。Claude に頼めば足す |
| 曖昧語が、別の語の一部に当たって止められる | 検査は部分一致。例: 曖昧語「しばらく」が、画面のボタン名「しばらく表示しない」に当たる | その行末に `<!-- check-docs: ignore 理由 -->` を書く。曖昧語として使っているなら言い換える（抑止しない） |
| 表記を統一したい語がある | 用語集にまだ無い | 「〇〇の表記を△△に統一して、用語集に足して」と頼む |
| コミットが「改訂の記録が無い文書を含むコミット」で止まる | 文書を直したのに、内部の改訂記録（`docs-style/history/`）に節が無い。スキルを通さずに直したときに起きる | Claude に「記録を足してからコミットして」と頼む。ほかのツールが直した変更のように記録が要らないと分かっているなら、そう伝える（Claude がコミットの文言に `doc-record: skip（改訂の記録なしでコミットする: <理由>）` を書き、ふつうのコマンドの実行確認と同じ画面で承認を求められる。画面のコマンドの中のこの文言を見て判断する） |
| コミットが「改訂設計書がこのコミットに入っていない」で止まる | 改訂設計書（`docs-style/plans/completed/`）をコミットに含めていない | 「改訂設計書も一緒にコミットして」と頼む |
| コミットが「別の呼び出しに分ける」で止まる | ファイルを書き換えるコマンドとコミットを1つにつないだ | Claude が分けてやり直す。利用者の操作は要らない |
