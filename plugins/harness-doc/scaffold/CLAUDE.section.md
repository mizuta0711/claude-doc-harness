## 文書ルール（harness-doc）

**読み手のための文書**（マニュアル・手順書・リファレンス・仕様書・README）を書くときの規律。
**書くより先に、読者が誰かを決める。**

対象は `.claude/doc-harness.config.json` の `include` に当たり、`exclude` に当たらない文書。
claude-dev-harness を併用している場合、設計書・機能設計書・レビュー記録・引き継ぎ（`docs/設計書/` ほか）は
**対象外**で、従来どおり harness-core のスキルが扱う。

1. **文書を書く・直す前に、必ず `/harness-doc:plan-doc` を使う。** 規模の判定を飛ばさない。どの工程を通すかは規模が決める
   （軽い修正なら工程は短く、事実確認・修正・同じ記述の横展開・改訂の記録で終わる。大きな作業は `manual-writer` に渡る）。
   **直前に直した文書への続けての依頼（「やっぱり前の書き方に戻して」「もう1行足して」）も、新しい依頼として `plan-doc` から始める。**
   会話の記憶で済ませると、前の改訂意図を読まずに戻したり、改訂の記録が抜けたりする
2. **事実は、コード・設定・実機の挙動から確認する。** 記憶や推測で書かない。
   手順に出てくるコマンドは実際に実行して、その出力を書く
3. **確認できなかった事実は断定しない。本文に「未確認」とも書かない。** 読者に正しい書き方にするか、その箇所を書かず、
   `<!-- 問い合わせ: Q1 -->`（番号だけ）の印を置いて完了報告の「問い合わせ」で依頼者に確かめる（仕様書は「未確認・未決事項」の節に書く）
4. **規模 M・L の文書は、完成前に `doc-reviewer` エージェントによる読者役レビューを通す。** 受け入れ基準で判定し、2回で終える。
   指摘は全件に「対応済み／見送り（理由）」を付ける。書く役とレビューする役は分ける（規模 S の小さな修正では省く）
5. 対象の文書（`.md` / `.html`）を書くと `check-docs` フックが曖昧語・見出し・コードブロックの言語指定・用語集・
   リンク切れを検査する。**失敗したら、指摘を直してから先へ進む。** 検査を抑止するのは
   `docs-style/README.md` に書いてある場合に限る。
   **文書は `Write` / `Edit` で書く。** Bash の python・sed・ヒアドキュメントで書き換えると、このフックが働かない
6. 用語は `docs-style/glossary.md` に揃える。新しい用語を用語集に足すときは、**先に依頼者に確かめる**。
   曖昧語は `docs-style/banned-words.txt` にある。使いたくなったら条件と値を書く
7. **文体と見た目は `docs-style/voice.md` に従う。** 既存の文書や CSS から読み取ったものを踏襲している。
   テイストを変えたいと頼まれても、本文を直接書き換えない。`plan-doc` がテイスト変更と判定し、`change-tone` に渡す
   （試作で合意してから、事実と構成を変えずに書き換える。voice.md は完了前の確認で採用が決まってから更新する）
8. **誰が読むか・何を扱わないかは、文書群ごとのブリーフ（`.claude/rules/doc-brief-*.md`）に従う。** 一度決めた読者を毎回聞き直さない。
   ブリーフは `.claude/` 配下なので `Edit` で書かず、harness-doc のスクリプト（`apply.mjs --brief`）で書く。
   読者や扱う範囲を変えたいと頼まれたら `/harness-doc:change-policy` を使う
9. **改訂の記録を必ず残す。** 内部の改訂記録（改訂箇所・改訂内容・改訂意図）は、すべての文書・すべての変更で必須。
   読者向けの改訂履歴がある文書には、いつ・どこを・どう変えたかを1行書く。記録は harness-doc のスクリプト（`history.mjs add`）で書く。
   **内部の改訂記録は読者役のレビューに渡さない**（書き手の意図が書いてあり、渡すと追認になる）
10. **規模 M・L は、改訂設計書（`docs-style/plans/`）で受け入れ基準と目次案の承認を取ってから書く。** L は目次の段階で読者役の点検を通し、試作で調子を合意してから全体を書く。完了したら `completed/` に移す。試作のファイル（`<名前>.proto-1.<拡張子>`）は承認の後に消す。
    文書を含むコミットは、改訂の記録が無ければフックが止める。止められたら記録を足してからコミットし直す。
    コミットの文言の `doc-record: skip（改訂の記録なしでコミットする: <理由>）` は依頼者の承認を求める印で、harness-doc の工程を通さない正当な変更のときだけ、依頼者に説明して使う

> 使い方の全体は [docs-style/README.md](docs-style/README.md) にある。
